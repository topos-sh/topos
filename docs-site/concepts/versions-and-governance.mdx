## Versions and `current`

A **version** is the sha-256 of a bundle's exact bytes. Versions are immutable and
content-addressed — `<skill>@<hash>` names those bytes and no others.

Each skill has exactly one **`current`** pointer: what the team is on. It only ever *moves*; nothing
is deleted when it does, so every move is invertible. Moves are compare-and-set against a generation
counter, so two people cannot race it — the loser is told the pointer moved and asked to look again.

```bash
topos log deploy                    # the version history
topos diff deploy <hash>            # a version against current
topos diff deploy <a>..<b>          # version against version
```

## Protection: `open` and `reviewed`

Protection decides what happens when a member publishes.

| Level | A member's publish |
|---|---|
| `open` | Lands directly — moves `current` (the default; small teams stay frictionless) |
| `reviewed` | Becomes a **proposal** awaiting an approver (the protected-branch model) |

```bash
topos protect deploy               # describe: tighten to reviewed
topos protect deploy --yes         # apply — reviewer or owner
topos protect deploy open --yes    # loosen — owner only
```

A skill follows the **workspace default** unless it has been pinned explicitly. Changing the
workspace default moves every skill still on it. The workspace default is the *Review gate* switch
in Settings → General; a per-skill pin lives on that skill's settings page.

<Note>
  **Never reject an intent the system can honor at a safer level.** A member publishing to a
  `reviewed` skill is not refused — the publish is *rerouted* into a proposal, and the receipt says
  so.
</Note>

Protection pressure scales with audience: `protect`'s describe tells you how many people the skill
reaches.

## Proposals

A proposal is a candidate version awaiting a verdict. It is the same object as any other version —
a proposal *is* a version that `current` has not moved to.

```bash
topos publish deploy --propose -m "why" --yes   # open one deliberately
topos review                                    # the inbox, across all workspaces
topos review deploy@<hash>                      # describe: author, message, base, diff
topos review deploy@<hash> --approve
topos review deploy@<hash> --reject -m "needs a test"
topos review deploy@<hash> --withdraw           # retract your own
```

- **`--approve`** moves `current` to the candidate, as a compare-and-set on the base the diff was
  computed against. If `current` moved while you were reviewing, the approval is refused and you look
  again — so what lands is exactly what was reviewed.
- **`--reject`** requires a reason (`-m`), which is carried back to the author.
- **`--withdraw`** is the author's own retraction.

In the browser, when the effective protection is `reviewed` and you are the proposer, Approve is
replaced by an explicit note that a *different* owner or reviewer must approve it — four-eyes, and
the server re-checks it.

<Warning>
  `--yes` is **not** meaningful on `review`. The verdict flag *is* the apply; a target with no verdict
  is the describe.
</Warning>

## Drafts

**One edited copy is the draft** — the delta between your working directory and the version last
applied there.

An update never destroys a draft. It snapshots on touch, then merges around it:

- **Clean merge** → you have a publishable draft on top of the new `current`, silently.
- **Conflict** → the full marker tree is written along with a durable conflict record, and the copy
  is frozen with a marked way out.

Two named exits:

```bash
topos update deploy --reset --yes         # discard YOUR edits, take current
topos update deploy --onto-current        # commit YOUR bytes onto current, dropping the merge
```

`--reset` is loss-led: its describe opens with exactly what will be lost, and it refuses to run
without a named skill — it will never reset everything at once. `--onto-current` requires exactly one
target, discloses the changes it is dropping, and always works offline.

## Revert

`revert` is the team-scoped rollback: it moves `current` **forward** to an older version's bytes.
Nothing is deleted, so it is invertible.

```bash
topos revert deploy --to <good-version>        # describe
topos revert deploy --to <good-version> --yes  # apply
```

`--to` names the **good** version you are going back *to*, never the bad one. It takes a full 64-hex
id or a unique prefix of at least 8 characters. It is gated exactly like publish: on a `reviewed`
skill a member's revert downgrades to a proposal.

The **local** go-back is a different verb with a different scope: `topos update deploy@<hash>` moves
only your machine.

Reverting is also available in the browser, on a skill's History tab, bound to the generation the
page was rendered against.

## The skill lifecycle

```
ACTIVE ──archive──► ARCHIVED ──delete──► DELETED (terminal, tombstoned)
   ▲                   │
   └────unarchive──────┘
```

<AccordionGroup>
  <Accordion title="Archive — owner, browser">
    The skill leaves circulation but not history. It is removed from every channel, excluded from
    delivery, its open proposals close, and the workspace renames it with a dated suffix — which
    **frees the base name for reuse**.

    Identity is safe under reuse: references key on the skill's id, so a reused name is a genuinely
    new identity with no lineage.

    On machines: the agent directories are cleaned at the next update, and the bytes plus your draft
    delta are retained locally so you can keep it as your own. Unarchive restores the base name if it
    is still free.
  </Accordion>
  <Accordion title="Delete — owner, browser, archive-first">
    The catalog row becomes a tombstone, version content is dropped, and the audit trail survives. It
    is a type-the-name confirmation.

    **Deletion cannot recall bytes.** Copies already on machines remain. The sessions page shows who
    still holds them — visibility, honestly, rather than a false promise.
  </Accordion>
  <Accordion title="Version purge — owner, browser, the leak tool">
    Drops **one** version's bytes. Its hash stays in history as a tombstone recording who purged it
    and when; reading or diffing against it explains itself. Only blobs no live version still needs
    are dropped, so content-addressed dedup never corrupts `current`. Purging the version that is
    still `current` is refused — publish or revert first.
  </Accordion>
</AccordionGroup>

### The secret-leak playbook

<Steps>
  <Step title="Publish a scrubbed version">
    Every machine's next sync replaces the leaked bytes fleet-wide. This is the fastest-acting step.
  </Step>
  <Step title="Watch the sessions page">
    Until every non-stale session reads current. Stale sessions and copies held by people who have
    left are **enumerated for you to chase by hand** — never silently omitted.
  </Step>
  <Step title="Rotate the credential regardless">
    This is the actual security action. Assume the bytes escaped.
  </Step>
  <Step title="Purge the poisoned versions">
    Last, once the pointer no longer needs them.
  </Step>
</Steps>

## Audit

Every mutation of shared state is attributed and audit-logged — including refused attempts, which are
recorded with a denied outcome so they never pollute the "last set by" line.

Channel history, skill history, and the version log are all readable in the browser; `topos log`
covers a skill from the CLI.
