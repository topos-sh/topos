All durable server state lives in **two volumes**. There are no secret files to back up beside them:
the vault is identity-free, and the internal bearer arrives by environment, never from disk.

| Volume | Mounted at | Holds |
|---|---|---|
| `pg-data` | `/var/lib/postgresql` | **Both schemas.** `web`: identity, seats, sessions, catalog, channels, profiles, invitations, proposals, receipts, audit, mail log. `plane`: the version index, `current` pointers, upload lifecycle |
| `plane-data` | `/data` | **The bytes.** `/data/git/<workspace>/` — one object store per workspace. `/data/large/<workspace>/objects` — size-routed large objects |

**The database is the source of truth for everything except bytes.**

<Warning>
  **Order matters: snapshot the bytes first, then the database.**

  A pointer in the database may name a byte that was written a moment ago. Take the bytes first and
  the worst case is a few unreferenced blobs — harmless. Take the database first and a pointer can
  name a byte your byte-snapshot missed, which is a real hole.
</Warning>

## Taking a backup

```bash
# 1. Bytes first
docker run --rm \
  -v topos_plane-data:/data \
  -v "$PWD":/backup alpine \
  tar czf /backup/plane-data-$(date +%F).tar.gz -C /data .

# 2. Then the database
docker compose exec -T db \
  pg_dump -U topos -d topos --format=custom > topos-$(date +%F).dump
```

Adjust the volume name for your compose project prefix — `docker volume ls` will show it.

A whole-volume snapshot works equally well for the database, as long as it is crash-consistent and
you keep the same ordering.

<Note>
  Using an external database? Your provider handles the metadata half, but **the `plane-data` volume
  is still yours to back up.** A managed-Postgres backup alone is not a backup of Topos.
</Note>

## Restoring

<Steps>
  <Step title="Bring the stack down">
    ```bash
    docker compose down
    ```
  </Step>
  <Step title="Restore the bytes volume">
    ```bash
    docker volume create topos_plane-data
    docker run --rm -v topos_plane-data:/data -v "$PWD":/backup alpine \
      tar xzf /backup/plane-data-2026-07-24.tar.gz -C /data
    ```
  </Step>
  <Step title="Restore the database, before serving anything">
    ```bash
    docker compose up -d db
    docker compose exec -T db pg_restore -U topos -d topos --clean --if-exists < topos-2026-07-24.dump
    ```
  </Step>
  <Step title="Bring the rest up">
    ```bash
    docker compose up -d
    ```
  </Step>
</Steps>

<Warning>
  **Restore the database before the app first serves a request.** On an empty database the first-boot
  ceremony mints a *new* workspace and prints a *new* claim link. That is not harmful, but it is
  confusing — and you would be looking at a different workspace than the one you restored.
</Warning>

Then verify:

```bash
curl -fsS https://topos.example.com/healthz
topos login https://topos.example.com
topos list --remote
```

## What a backup does not cover

<AccordionGroup>
  <Accordion title="Copies already on machines">
    Deliberately. Delivered skills live in each person's agent directories, outside Topos's reach —
    which is also why deleting a skill "cannot recall bytes." Restoring the server does not touch
    them, and a machine that syncs after a restore converges to whatever the restored workspace says
    is current.
  </Accordion>
  <Accordion title="Client credentials">
    The one at-rest client secret is `~/.topos/identity/sessions.json` (mode `0600`) on each machine.
    Losing it just means logging in again — do not back it up.
  </Accordion>
  <Accordion title="Your environment file">
    `.env` is yours to keep safe. `TOPOS_WEB_AUTH_SECRET` in particular: rotating it invalidates every
    signed-in browser session.
  </Accordion>
</AccordionGroup>

## Exporting content

For a content-level export — every skill at its current version plus a manifest, as one zip — an
owner can use **Settings → General → Export skills** in the browser.

That is a portability tool rather than a backup: it carries the bytes people care about, not the
identity, policy, history, or audit trail.

## Encryption at rest

Not implemented, deliberately: disk or volume encryption on the server is the operator's
responsibility and the right layer for it. The client-side session file is likewise plaintext at mode
`0600` — full-disk encryption is the answer there too.
