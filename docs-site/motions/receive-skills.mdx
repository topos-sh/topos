## Ask for a skill

`topos add` is the demand-side edit. It records a manifest line **and delivers in the same
invocation**.

```bash
topos add code-review                 # a bare catalog name, unique across your sessions
topos add @acme/code-review           # explicit workspace
topos add @acme/channels/backend      # a whole channel's set
topos add topos.sh/acme/code-review   # canonical — or a pasted page URL
topos add @acme/deploy@<64-hex>       # pinned to exact bytes
```

The line goes into the **nearest `topos.toml`** covering your current directory. If none is in reach,
one is created at the enclosing git root — commit it, it is the recipe that gives every teammate's
agents the same set in this repo.

### Project scope or person scope

<CardGroup cols={2}>
  <Card title="Project" icon="folder">
    ```bash
    topos add code-review
    ```
    Writes `topos.toml` in the repo. Everyone working in this project gets it — including teammates
    who never ran the command.
  </Card>
  <Card title="Person (-g)" icon="user">
    ```bash
    topos add code-review -g
    ```
    Writes your **server-stored profile** for that workspace. It follows you to every machine you log
    in, and is editable in the browser.
  </Card>
</CardGroup>

`-g` with a local path writes `~/.topos/topos.toml` instead — a path cannot live on the server.

Other sources `add` accepts: a local folder (`topos add ./tools/my-skill`, adopted in place, offline,
no account) and a GitHub repo (see [Import from GitHub](/motions/import-from-github)).

## Where bytes land

Placement is derived from which harnesses are actually detected on the machine, not configured by
hand.

**Person scope** — shared-directory-first under `$HOME`:

- one copy in `~/.agents/skills/<name>` when at least one detected harness reads that shared
  convention, **plus**
- one native copy per detected harness that does not.

**Project scope** — the same policy rooted at your checkout:

- `<project>/.agents/skills/<name>` for harnesses covered by the shared convention,
- the harness's own project directory otherwise (`.claude/skills`, `.factory/skills`, …),
- `<project>/.claude/skills` as the default shape when nothing is detected.

A `[placement]` entry in `topos.toml` overrides this with one project-relative directory. See
[Harness integration](/harnesses/how-it-works) for the full directory table.

### Kept out of your commits

Every landed **project** placement appends one line to `.git/info/exclude`:

```
# topos-managed skills (placed by `topos update`; not committed)
/.claude/skills/code-review/
```

It is idempotent, and it resolves the real git directory correctly through a `.git` file or a linked
worktree. **Committed ignore files are never touched** — `.gitignore` is yours.

If the exclude cannot be written, you get a warning, never a failed update.

### Never clobbered

A directory is only ever chosen when it is free, or when Topos's own record already owns it. If an
occupant happens to be a byte-identical copy of the incoming version, it is **adopted in place**
rather than duplicated. If a harness stops being detected, its placement is **frozen**, never
deleted.

Name collisions across workspaces are resolved by suffixing the workspace (`deploy-acme`), then a
counter.

## Updates arrive by themselves

Logging in arms a session-start trigger that runs the sweep:

```
command -v topos >/dev/null 2>&1 && topos update --quiet || true  # topos:currency
```

So at the start of each agent session, the machine reconciles. Run it by hand any time:

```bash
topos update              # the full sweep
topos update code-review  # one resolved line
topos update --quiet      # exactly what the hook runs
```

What a sweep does: dial each live session's delivery once, build the layer chain for your current
directory, resolve demand against entitlement, land what changed, retire what nothing demands
(snapshotting first), and report the applied state back.

<Note>
  **A quiet sweep is designed never to break a session start.** It self-throttles (default 300s, set
  with `--ttl` or `TOPOS_UPDATE_TTL`, `0` disables), emits nothing when nothing changed, and an
  auth or network blip warns and exits `0`. A pending session skips quietly. An unreachable server
  falls back to the offline cache so the local converge still happens.
</Note>

## Your edits are never overwritten

Edit a delivered skill and Topos treats the difference as a **draft**. An update snapshots it, then
merges around it:

- **Clean** → your draft now sits on top of the new `current`, silently, ready to publish.
- **Conflict** → the full marker tree is written with a durable conflict record, and the copy is
  frozen with a named way out.

```bash
topos diff code-review                      # what you changed
topos update code-review --reset --yes      # discard yours, take current
topos update code-review --onto-current     # keep yours, drop the pending merge
```

`--reset` opens with exactly what will be lost and refuses to run without naming a skill. Both exits
are disclosed before they act.

## Go back on this machine only

```bash
topos update code-review@9f2c1a8b   # local go-back to those bytes
```

A hex suffix is recognized from 8 characters up. This changes **your machine only** — the team-scoped
rollback is [`topos revert`](/motions/roll-back).

## See what you have

```bash
topos status                 # the trust rail: per skill, one source line and an honest state
topos list                   # inventory, including untracked skills sitting in harness dirs
topos list --remote          # your workspaces' catalogs, annotated with local state
topos list --footprint       # every path topos owns outside skill dirs
topos list --json            # 50 rows per bucket by default; --limit 0 for all
```

`status` states, per bundle: the winning reference, the **one** manifest that asked for it, its
scope, and its state — plus `shadows …` and `excluded by …` sub-lines that name the layer
responsible.
