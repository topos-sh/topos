A project commits two files at the repo root. `topos.toml` states **intent** — what this repo's
agents use, and whether each thing follows the team's current version or stays pinned.
`topos.lock` records **resolution** — exactly which version of each thing this repo runs. The
same relationship as `package.json` and `package-lock.json`.

```toml title="topos.toml — committed at the repo root"
schema = 1
workspace = "topos.sh/acme"

[skills]
code-review     = "latest"                       # follows the team's current version
release-process = "4c9f0b21…(64 hex)"            # pinned to one version
find-skills     = "github:vercel-labs/skills"    # a repo skill; the key is the skill's name
local-notes     = "./tools/local-notes"          # a folder in this repo

[mcp]
linear = "latest"

[channels]
backend = "latest"
```

`topos init` creates it (writing the `workspace = ` line from your default workspace); the CLI
writes its lines. `topos install` places exactly what the lock records; `topos update` moves the
lock and shows the diff.

## One workspace per project

The `workspace = "<host>/<workspace>"` line names the ONE workspace this project's bare keys
resolve against — the way a checkout has one origin. `code-review` under `[skills]` means
`topos.sh/acme/code-review`. A project cannot name a second workspace; rows from GitHub
(`github:owner/repo`) and folders in the repo (`"./tools/x"`) need no workspace at all, so a
file holding only those may omit the line.

## What a value can say

The same four spellings fit every row:

- `"latest"` — follow: `topos update` moves this row to the team's current version and records
  the move in the lock. Nothing else does.
- a version — pinned: the full 64-hex version for a workspace bundle
  (`topos add code-review@<version>` writes it), or `github:owner/repo#<commit>` for a repo
  skill. `topos update` skips pinned rows.
- a path (`"./tools/x"`) — a folder in this repo, delivered as-is.
- an inline table for the rarer fields: `{ version = …, dest = […], name = …, subdir = …,
  kind = … }` (`source = "github:…"` and `path = "./…"` name the row's origin in table form).
  `dest` freezes placement to the folders it names — relative, inside the checkout.

## topos.lock

Generated, committed, and deterministic — one alphabetically-sorted block per entry, no
timestamps, so two branches that update different bundles merge cleanly. On a conflict, run
`topos update`: it re-resolves and rewrites the file.

```toml title="topos.lock — generated; commit it"
schema = 1
workspace = "topos.sh/acme"

[channels.backend]
members = ["deploy-checklist", "lint-rules"]

[mcp.linear]
revision = "mcpr_8f4e21c9"

[skills.code-review]
version = "3a1f0b62…(64 hex)"

[skills.deploy-checklist]
version = "ab12cd34…(64 hex)"
via = "backend"

[skills.find-skills]
source = "github:vercel-labs/skills"
commit = "9d0e8c1c2f4a5b6d"
```

Reading it: a skill a channel brings carries `via`; a channel is its frozen member list — the
members' own blocks hold the versions. What the team publishes later changes nothing here until
someone runs `topos update` and commits the diff; rolling a bad update back is `git revert` on
that commit, and every machine follows.

`topos install` fills a lock entry for a `topos.toml` line the lock does not know yet — resolved
once, at the team's then-current version — and never moves an existing entry. In CI, run
`topos install --frozen`: it fails instead of writing when the two files disagree, when anything
cannot be fetched, or when a checksum does not match.

## Rows that name an MCP server

A shared server is a `[mcp]` row; delivery writes each agent's own config format. A machine-local
server you run from a folder is a path row with the kind spelled out:

```toml
[mcp]
weather = { path = "./tools/weather-server", kind = "mcp" }
```

The lock records the catalog revision each shared server resolved to, and `topos install`
converges the entry to that revision exactly as it converges a skill to its version — a fresh
checkout writes the configuration a teammate received then, not whatever the catalog serves
today. `topos update` is what moves it.

## Your machine's own file

`~/.topos/topos.toml` is the same sections with two differences: there is no `workspace = ` line
— it can hold bundles from any workspace, so workspace keys are spelled in full
(`"topos.sh/acme/code-review"`) — and one extra section exists:

```toml title="~/.topos/topos.toml"
schema = 1

[workspaces]
"topos.sh/acme" = "latest"    # everything this workspace currently gives you

[skills]
"topos.sh/acme/noisy-skill" = "off"    # the personal switch
```

`topos login` writes a workspace's `[workspaces]` row on this machine's first connection and
never re-adds one you delete. There is no lock at machine level — what follows you personally
stays current on its own; the repo is the deterministic scope. `"off"` is machine-only: a
project keeps a bundle out by removing the row that brings it.

## Which commands write which lines

- `topos init` — the file itself, with the `workspace = ` line.
- `topos add <name>` — a `[skills]`/`[mcp]`/`[channels]` row, `"latest"`; `add <name>@<version>`
  writes the pin; `add <owner>/<repo>` writes one row per skill the repo holds.
- `topos remove <name>` — the exact inverse.
- `topos install` — `topos.lock` entries for rows the lock lacks; nothing else.
- `topos update [<name>]` — the lock, rewritten from what "latest" now resolves to.
- `topos login` — the machine file's `[workspaces]` row, first connection only.

## Editing by hand

Welcome, in either file's `topos.toml` — the CLI treats your edit exactly like its own writes,
and `topos fmt` tidies the layout (sections ordered, keys sorted, comments kept). Hand-editing
`topos.lock` is like hand-editing any lockfile: legal, but `topos update` is the tool.

## Which file governs

The nearest `topos.toml` at or above your working directory governs that checkout WHOLE — no
merging with a parent's file or your machine's. Outside any project, your machine file and your
workspaces' feeds govern. One bundle named by both scopes is delivered twice, one copy per
scope, each with its own state.
