Topos puts the same files wherever each agent on your machine looks for skills, and
refreshes them at the right moment — so Claude Code, Cursor, and everything else you run
work from the same shared set, with no per-agent setup.

Nothing is translated between agent formats: a skill is a plain directory, and supporting
an agent means knowing **which directories it reads and when to refresh them**. There is
also no second permission system — how much a human sits in the loop belongs to your agent,
not to Topos.

## Three tiers of support

- **auto-update** — Topos installs an update trigger inside the agent (a session-start hook,
  or a scheduled job where that's what the agent offers), so managed skills refresh without
  you asking. Exactly when a refresh becomes visible depends on the form: a session-start hook
  has the new bytes on disk before the session begins work; OpenClaw's scheduled job catches
  up within about a minute; and Hermes builds its skill index once per process, so changed
  content is picked up immediately but a brand-new skill appears at the next cold start.
- **delivery** — no trigger in that agent, but every managed skill is still placed into its
  skills directory and refreshed by *every* update on the machine — another agent's trigger,
  or a manual `topos update`.
- **discover + add** — project-scoped conventions only: Topos can find and adopt skills
  sitting there, but has no machine-wide place to deliver into.

<Note>
  Some agents require **their own one-time approval** before they run an installed trigger
  (Codex trusts hooks in-app via `/hooks`; Gemini CLI confirms new hooks; Goose enables
  plugins itself). Until you grant it the trigger sits there and never fires, and the agent
  behaves like the delivery tier. `topos status` answers whether the trigger is *installed* —
  it reports `armed` as soon as the artifact is in place — so it cannot tell you an approval
  is still outstanding. That step is yours to complete in the agent.
</Note>

## The trigger

Every trigger runs the same base sweep — `topos update --quiet` — registered in whatever form
the agent accepts. Claude Code's line adds a short flag naming itself, which is how that agent
opts into the extra answer described below; every other trigger runs the sweep unadorned.

Two separate things decide whether a failed sweep ever reaches the agent. First, what `topos`
itself does: an unreachable server or a login that has ended is treated as a soft failure —
reported quietly, exit `0` — while a genuinely local problem, like a corrupt file or a failed
write, exits non-zero. Second, whether the trigger's form passes that through. A shell hook
wraps the sweep in a guard that skips it when the `topos` binary isn't there and a tail that
exits `0` regardless, so the agent sees success either way; a plugin hook calls the sweep from
the plugin's own code and swallows errors there, with the same effect. Only the plain-command
form — run as-is under the agent's own timeout, with no wrapper — lets a non-zero exit reach
the agent. The deliberate result is that a best-effort update almost never surfaces as a
session-start error.

The sweep self-throttles (default 300 seconds), so a trigger can fire on every session event
cheaply. It also stays off the network it doesn't need: it talks to your workspaces and to nothing
else, so a skill imported from a git repo moves only when you run `topos update` yourself, never
because a session started.

It speaks only when there is something worth saying: skills actually changed, or
there is a fact you shouldn't miss — a workspace this machine can no longer reach, say, whose
skills are now frozen in place. With neither, it prints nothing at all. When it does speak, it
uses the narrowest shape the calling agent is known to accept, because some agents check hook
output against a strict schema and treat anything unexpected as a failed hook. Claude Code —
the agent that names itself in its trigger — is the one that additionally gets asked to
re-scan its skills, which is what makes freshly pulled skills usable in the session already
open; it is asked only when skills really did change.

An ownership marker written alongside each trigger is how Topos recognizes its own and never
touches yours. Triggers are installed when Topos wires into an agent (a completed login, an
adopt) and removed by `topos uninstall --yes`. Removal is confirmed for the triggers that live
in a config file Topos can read; where one lives behind an agent's own service and that
service isn't reachable at the time, Topos reports the removal as unconfirmed — a scheduled job
may survive and resume — rather than claiming it is gone. Every adapter is idempotent and fails
closed: if a config file's shape can't be proven, Topos reports it honestly and writes nothing.

## Where the files land

**For you** (the skills that follow you from machine to machine), under `$HOME`:

- one copy in `~/.agents/skills/<name>` where a detected agent reads that shared convention,
- plus one native copy per detected agent that doesn't.

**Per project** (skills from a repo's `topos.toml`), rooted at the checkout:

- `<project>/.agents/skills/<name>` for agents covered by the shared convention,
- the agent's own project directory otherwise (`.claude/skills`, `.factory/skills`, …),
- `<project>/.claude/skills` as the default when nothing is detected.

A committed `topos.toml` can override that with one project-relative directory instead — per entry
or for every skill the file asks for:

```toml title="topos.toml"
[bundles]
"topos.sh/acme/code-review" = { version = "*", path = "prompts/skills" }

[defaults.skill]
path = ".agents/skills"
```

The value must stay inside the checkout: a file everyone commits can never aim managed bytes
somewhere else on a contributor's disk, and one that tries is ignored with a warning.

Delivered project folders keep **themselves** out of commits — each one carries a one-line
`.gitignore` of its own, the way `node_modules` does. Nothing under `.git/` is written, and an
ignore file you committed is never touched. Topos's own bookkeeping for the checkout lives in
`<project>/.topos/`, which ignores itself whole. A directory is only chosen when it's free or
already Topos-managed — a byte-identical occupant is adopted in place, never duplicated.

## The current state, honestly

- **Placement** reaches every detected agent in the table below — that tier is broad.
- **Full adapters** (placement + trigger management + discovery) exist for Claude Code,
  OpenClaw, and Hermes Agent; the active adapter constructed today is **Claude Code**.
- **Triggers** are additionally installed for Amp, Cline, Codex, Cursor, Droid, Gemini CLI,
  GitHub Copilot, Goose, and OpenCode.
- Some trigger shapes are confirmed against a live build; others follow vendor
  documentation. `topos status` tells you the truth for your machine — per agent: `armed`,
  `not armed`, or `unknown`.

## The shared directory

`~/.agents/skills` is a cross-agent convention. Where a detected agent is known to read it,
Topos places **one** copy there instead of a native copy per agent — several agents on one
machine share the same files. Coverage is tracked with provenance and fails closed: an agent
whose support is unknown gets its own native copy.
