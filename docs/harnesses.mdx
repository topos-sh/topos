Topos never touches an agent you did not pick. You name the agents you use, and from then on
Topos puts the same files wherever each of them looks for skills and refreshes them at the right
moment. Nothing is translated between agent formats: a skill is a plain directory, and supporting
an agent means knowing **which directories it reads and when to refresh them**. There is no second
permission system either: how much a human sits in the loop belongs to your agent, not to Topos.

## Pick your agents

```bash
topos init -a claude-code -a codex     # use these two in this project
topos agents                           # the pick here, and what is installed on this machine
topos agents add cursor                # add one, and install for it now
topos agents remove cursor --yes       # drop one, and delete what Topos put there
```

The pick is per project and personal. It lives in `<project>/.topos/agents.json`, which keeps
itself out of git, so a teammate who clones the same repo picks their own agents. Repeat `-a` for
several, or write `-a '*'` for every agent installed on this machine. Add `-g` to any of these
commands and the choice is your machine's instead, recorded in `~/.topos/agents.json`.

The two scopes are independent. A project reads its own file, `-g` reads the machine's, and
neither falls back to the other. A machine-wide pick never decides what a checkout gets, so a
fresh clone picks for itself.

With no `-a`, the one agent installed here is used and Topos says which. Topos never prompts.
With several installed and none picked here it names the installed agents and the command that
records the choice, then stops with exit `2`. That is the same answer on a terminal, in a pipe,
and under `--json`. Inside an agent that announces itself, such as Claude Code, that agent is
picked silently, so nothing stops there.

With no agent installed at all there is nothing to choose from. The command runs, records what
you asked it to record, places nothing, and says so. Pick an agent later and the next run places
everything for it. `install --frozen` behaves the same way where several agents are installed and
none is picked: it fetches and verifies what the lock records, places none of it, and exits `0`.

## Three tiers of support

What Topos can do for an agent, once you have picked it:

- **auto-update** — Topos installs an update trigger inside the agent (a session-start hook,
  or a scheduled job where that's what the agent offers), so managed skills refresh without
  you asking. When a refresh becomes visible depends on the form: a session-start hook has the
  new bytes on disk before the session begins work; OpenClaw's scheduled job catches up within
  about a minute; Hermes builds its skill index once per process, so changed content is picked
  up immediately but a brand-new skill appears at the next cold start.
- **delivery** — no trigger in that agent, but every managed skill is still placed into its
  skills directory and refreshed by *every* update on the machine — another agent's trigger,
  or a manual `topos update`.
- **discover + add** — project-scoped conventions only: Topos can find and adopt skills
  sitting there, but has no machine-wide place to deliver into.

<Note>
  Some agents require **their own one-time approval** before they run an installed trigger
  (Codex trusts hooks in-app via `/hooks`; Gemini CLI confirms new hooks; Goose enables
  plugins itself). Until you grant it the trigger sits there and never fires, and the agent
  behaves like the delivery tier. `topos status` answers whether the trigger is *installed* —
  it reports `registered` as soon as the artifact is in place — so it cannot tell you an approval
  is still outstanding. That step is yours to complete in the agent.
</Note>

## The trigger

Every trigger runs the same base sweep, registered in whatever form the agent accepts:

```bash
topos install --quiet
```

What lands in the agent's config is that sweep plus a **marker** naming the agent it was written
for. The marker is how Topos recognises its own entry on a later run, and Claude Code's is also
what opts that agent into the extra answer below. It is not a flag you type, and it is not the
same on every agent.

The sweep self-throttles (default 300 seconds), so a trigger can fire on every session event
cheaply. It always covers **both** sets — your machine-wide one and any `topos.toml` covering the
folder the session starts in — so nothing goes stale while you spend the day in one checkout. That
is the one way it differs from a `topos update` you type, which converges the scope you are standing
in. The sweep also stays off the network it doesn't need. Your workspaces answer about every skill
at once, so they are asked on the throttle above; a GitHub repository answers about itself alone, so
those lines are checked on their own much slower rhythm — a few times a day, spread out so a fleet
of machines doesn't arrive at once — and the check asks what commit the repo is on before deciding
whether anything is worth downloading. `topos status` shows when each source was last checked and
whether it answered; `topos list` names the source on every row it delivers, and marks the rows a
stopped source froze — `[not responding]`, with the last time it answered.

It speaks only when there is something worth saying — skills actually changed, or there is a fact
you shouldn't miss, like a workspace this machine can no longer reach whose skills are now frozen
in place. With neither, it prints nothing at all. When it does speak it uses the narrowest shape
the calling agent is known to accept, because some agents check hook output against a strict schema
and treat anything unexpected as a failed hook. Claude Code — the agent that names itself in its
trigger — is the one additionally asked to re-scan its skills, which is what makes freshly pulled
skills usable in the session already open; it is asked only when skills really did change.

Two things decide whether a failed sweep reaches the agent. First, `topos` itself: an unreachable
server or a login that has ended is a soft failure — reported quietly, exit `0` — while a genuinely
local problem, like a corrupt file or a failed write, exits non-zero. Second, the trigger's form: a
shell hook wraps the sweep in a guard that skips it when the `topos` binary isn't there and a tail
that exits `0` regardless; a plugin hook swallows errors in the plugin's own code. Only the
plain-command form — run as-is under the agent's own timeout, with no wrapper — lets a non-zero
exit through. The deliberate result: a best-effort update almost never surfaces as a session-start
error.

An ownership marker written alongside each trigger is how Topos recognizes its own and never
touches yours. A trigger is written when you pick that agent, by `topos init -a <agent>` or
`topos agents add <agent>`, and taken away by `topos agents remove <agent>`, or by
`topos uninstall --yes` for the machine and for the checkout you run it in (other checkouts keep
theirs until you run `topos agents remove` there). Nothing else writes one: signing in does not, and neither does adding a
skill. Install a new agent today and Topos leaves it alone until you pick it.

Removal is confirmed for triggers living in a config file
Topos can read; where one lives behind an agent's own service and that service isn't reachable at
the time, Topos reports the removal as unconfirmed — a scheduled job may survive and resume —
rather than claiming it is gone. Every adapter is idempotent and fails closed: if a config file's
shape can't be proven, Topos reports it honestly and writes nothing.

## One folder per agent

Each agent you pick gets its own folder: its skills sit next to its MCP config and its
auto-update hook. Claude Code is the one exception, and only for MCP servers, which it reads from
a file of its own outside the checkout.

Per project, rooted at the checkout:

| Agent | Skills | MCP servers | Auto-update hook | `--gitignore` adds |
|---|---|---|---|---|
| Claude Code | `.claude/skills/` | `~/.claude.json`, in its section for this checkout | `.claude/settings.local.json` | `.claude/` |
| Cursor | `.cursor/skills/` | `.cursor/mcp.json` | `.cursor/hooks.json` | `.cursor/` |
| Codex | `.codex/skills/` | `.codex/config.toml` | `.codex/hooks.json` | `.codex/` |
| OpenCode | `.opencode/skills/` | `.opencode/opencode.json` | `.opencode/plugin/topos.ts` | `.opencode/` |

Machine-wide (`-g`) is the same shape per agent under `$HOME`: `~/.claude/skills` with
`~/.claude/settings.json` and `~/.claude.json`; `~/.cursor/skills` with `~/.cursor/hooks.json` and
`~/.cursor/mcp.json`; `~/.codex/skills` with `~/.codex/hooks.json` and `~/.codex/config.toml`;
`~/.config/opencode/skills` with `~/.config/opencode/plugin/topos.ts` and
`~/.config/opencode/opencode.json`.

A project pick writes inside that checkout, with one exception. Claude Code reads project MCP
servers only from `~/.claude.json`, so that is where they go, and [MCP servers](#mcp-servers)
below says what that looks like and how to get a committed file in the repo instead. No skills
folder and no hook is ever written under your home directory for a project pick. `-g` is the
mirror image, writing under `$HOME` and never into a checkout. In both scopes an agent you did not
pick gets nothing at all, whether or not it is installed here. A directory is only chosen when it
is free or already Topos-managed: a byte-identical occupant is adopted in place, never duplicated.

Any other agent from the [table below](#the-agent-table) can be picked too. It gets its skills
folder, and its MCP entry where it has a project config. No project hook exists for it, so the
receipt says so and names the two ways to keep it fresh: run `topos update`, or pick that agent
with `-g` and let its machine-wide hook do it.

Codex runs a project hook only once you have trusted that repository inside Codex, and the receipt
says so when it writes one.

## Keeping the files out of git

Two things need no thought. `<project>/.topos/`, where Topos keeps its bookkeeping and your pick,
ignores itself whole. Every delivered skill folder carries a one-line `.gitignore` of its own, the
way `node_modules` does. Topos writes nothing under `.git/`, and never touches an ignore file you
wrote.

Committing those folders instead is a fine choice. The hook line is safe in a repo other people
clone: without the `topos` binary on `PATH` it does nothing, and it exits `0` either way. It is the
sweep, a `command -v topos` guard, an exit-`0` tail, and the agent's marker. Cursor's, for instance:

```bash
command -v topos >/dev/null 2>&1 && topos install --quiet --from cursor || true
```

Commit it exactly as Topos wrote it. Each agent's marker is its own, and a retyped line is one
Topos no longer recognises as its own entry.

To ignore the agents' folders whole, ask for it once. It is off by default, and it is the only
time Topos edits a `.gitignore`:

```bash
topos init --gitignore
topos agents --gitignore
```

That appends the last column of the table above, for the agents you picked, one line each. Run it
again and nothing is written twice.

A committed `topos.toml` can freeze placement per entry instead. `dest` names the exact
project-relative folders a line delivers into, and the pick stops deciding for it:

```toml title="topos.toml"
workspace = "topos.sh/acme"

[skills]
code-review = { dest = ["prompts/skills"] }
```

Each entry must stay inside the checkout — relative, no `..`, not absolute — because a file
everyone commits can never aim managed bytes somewhere else on a contributor's disk; one that
tries refuses at load, naming the entry and the rule.

## MCP servers

A skill is files; an [MCP server](/docs/mcp) is an address. Sixteen agents have an MCP config
surface, and for those Topos writes **one entry per agent** — under a stable `topos-`-prefixed key
— instead of placing a directory. Everything else here still applies: Topos writes only its own
entries, an agent you did not pick gets nothing, and a file whose shape can't be proven safe is
left alone.

| Agent | User-scope config | Project-scope config | Picked up | Sign-in |
|---|---|---|---|---|
| Claude Code | `~/.claude.json` † | `~/.claude.json`, in its section for this checkout | next session | `/mcp` |
| Claude Desktop | `~/Library/Application Support/Claude/claude_desktop_config.json` ◊ | — (none) | quit completely and reopen | in the app, on first use |
| Cline | `~/.cline/data/settings/cline_mcp_settings.json` | — (none) | automatically; Cline watches the file | Cline's own, on first use |
| Codex | `~/.codex/config.toml` † | `.codex/config.toml` ‡ | restart `codex` | `codex mcp login <name>` |
| Cursor | `~/.cursor/mcp.json` | `.cursor/mcp.json` | restart Cursor | Cursor's own, on first use |
| Gemini CLI | `~/.gemini/settings.json` | `.gemini/settings.json` | restart `gemini` | Gemini's own, on first use |
| GitHub Copilot CLI | `~/.copilot/mcp-config.json` | — (none) | next `copilot` run; `/mcp` lists them | Copilot's own, on first use |
| Goose | `~/.config/goose/config.yaml` † | — (none) | restart your goose session | Goose's own, on first use |
| Hermes Agent | `~/.hermes/config.yaml` † | — (none) | `/reload-mcp` in a session, or next session | the entry declares `auth: oauth` |
| LM Studio | `~/.lmstudio/mcp.json` | — (none) | automatically, when the file is saved | LM Studio's own, on first use |
| OpenCode | `~/.config/opencode/opencode.json` † | `.opencode/opencode.json` | restart `opencode` | automatic on the first `401` |
| OpenClaw | `~/.openclaw/openclaw.json` | — (none) | automatically | `openclaw mcp login <name>` |
| Roo Code | VS Code's storage for the Roo extension ◊ | `.roo/mcp.json` | automatically; Roo watches the file | Roo's own, on first use |
| VS Code | `~/Library/Application Support/Code/User/mcp.json` ◊ | `.vscode/mcp.json` | restart the server from the MCP view | VS Code's own, on first use |
| Windsurf | `~/.codeium/windsurf/mcp_config.json` | — (none) | press refresh in Cascade's MCP panel | Windsurf's own, on first use |
| Zed | `~/.config/zed/settings.json` † | — (none) | automatically | Zed's own, on first use |

† `$CLAUDE_CONFIG_DIR`, `$CODEX_HOME`, `$HERMES_HOME`, and `$XDG_CONFIG_HOME` move these roots,
exactly as they move the skills directories above. By default `.claude.json` sits beside
`~/.claude/`; with `$CLAUDE_CONFIG_DIR` set it moves inside that directory.

‡ Codex reads a project config only once you have trusted that repository inside Codex.

◊ These three keep their files where each platform keeps application settings, so the path shown is
the macOS one. On Linux it is under `~/.config` (`~/.config/Code/User/mcp.json`), on Windows under
`%APPDATA%`. Because that path has no single spelling, `-a vscode`, `-a roo` and `-a claude-desktop`
cannot name it at machine scope — write the path out with `--dest` instead.

Each file is written in its own dialect and nothing else in it is disturbed: JSON stays JSON,
VS Code's and Zed's and OpenClaw's keep their comments and trailing commas, Codex gets a
`[mcp_servers.…]` table, Hermes and Goose get a one-line entry under their own key.

Claude Code keeps both scopes in that one file. `mcpServers` at the top level is what every
session sees; `projects."<the checkout's own path>".mcpServers` is what only a session started in
that exact directory sees. Topos edits the slot for the scope it is acting in and leaves every
other byte alone, sign-in and trust decisions included.

Two things come out of "that exact directory". A session you start in a subdirectory of the repo
does not see those servers. Neither does a teammate who clones the repo, because that file is
yours and is not in git. `--dest .mcp.json` writes the committed file in the repo root instead,
which every session under the repo reads. Committing that file is how a server reaches your
teammates:

```bash
topos add weather --dest .mcp.json
```

A `topos.toml` row spells the same choice as `dest = [".mcp.json"]`. Re-aiming a row that already
placed an entry moves later writes only: the entry standing in `~/.claude.json` is left where it
is, named on the receipt, and deleting it is yours.

An entry an older Topos put somewhere else moves on the next update. Claude Code's comes out of
the `~/.claude/skills/topos-mcp/` directory Topos used to create, and lands under the same
`topos-` key every other agent gets, so the tools are named for the server rather than for that
directory. OpenCode's comes out of the `opencode.json` in the repo root. Nothing is said on the
receipt, because the bundle did not leave. The old file goes with the last entry Topos put there,
and one holding anything of yours stays exactly as it is.

The entry's exact shape is each agent's own, down to details that decide whether it works at all:
VS Code keeps servers under `servers` rather than `mcpServers`, Windsurf spells the address
`serverUrl`, Goose calls it `uri`, and Cline and Roo need the transport named — `streamableHttp`
and `streamable-http` respectively — because leaving it out means the old SSE transport, silently.
A program splits the same way: Hermes writes the usual `command`, `args` and `env`, while Goose
spells them `cmd`, `args` and `envs` and marks the entry `type: stdio`.

Nine of the sixteen have **no project-level MCP config** — the rows marked `— (none)` above — so a
project row reports `not placed — no project-level config` for them rather than falling back to
your home config. They receive the same server through your machine-wide scope.

Two of them reach a server exactly one way. **Claude Desktop** adds remote servers in the app, not
in this file, so a shared address reaches it as a local bridge process instead. **LM Studio** is the
mirror image: Topos can give it an address, and a bundle that ships only a package reports
`not placed` there — LM Studio documents local servers but publishes no entry grammar for one, and
the shape stays unwritten until a real build confirms it.

<Note>
  Signing in is the agent's own act, on your own machine. A shared MCP bundle carries no credential
  and no slot for one — Topos refuses documents that do — so a server behind OAuth is authorized
  once per person, per machine, in whichever agent is calling it.
</Note>

## The current state, honestly

- **Placement** works for every agent in the table below. Pick one and its skills folder is
  filled; leave it out and Topos never writes there.
- **A project auto-update hook** exists for Claude Code, Cursor, Codex, and OpenCode. Any other
  agent you pick in a project still gets its skills; its hook can only be machine-wide (`-g`).
- **Machine-wide triggers** also cover Amp, Antigravity CLI, Cline, Devin for Terminal, Droid,
  Gemini CLI, GitHub Copilot, Goose, Grok Build, Hermes Agent, Kilo Code, Kimi Code CLI,
  OpenClaw, Pi, and Qoder.
- Some trigger shapes are confirmed against a live build; others follow vendor documentation.
  `topos status` tells you the truth for your machine, per picked agent: `registered`,
  `not registered`, or `not checked`.

  Don't see yours? Skills are plain directories, so any agent that reads a skills folder
  picks up delivered bundles whether or not it's listed. `topos list` also finds the skills
  already sitting in these directories that it doesn't manage — a bare run counts them in one
  line, `topos list --untracked` names them, and `topos add <name>` takes one over.
</Note>

## Folders more than one agent reads

`.agents/skills` and `~/.agents/skills` are cross-agent conventions, and several rows above name
them. Two picked agents whose folders are the same get one copy, not two.

Agents also overlap in what they read beyond their own folder. Codex reads both `.codex/skills`
and `.agents/skills` and deduplicates nothing between them, which is exactly why Topos writes
Codex's own folder and only that one: a skill sitting in both would be listed twice in Codex
alone. Cursor reads `.claude/skills` and `.codex/skills` as well as its own, and OpenCode reads
`.claude/skills` and `.agents/skills`.

So with several agents picked, one of them may list the same skill twice. Pick both Cursor and
Codex in one project and Cursor lists each skill twice, once from `.cursor/skills` and once from
`.codex/skills`. That is their behaviour, not a conflict: the bytes are identical everywhere, and
frontmatter fields an agent does not know are ignored, never run. The layout in the table above is
the one that keeps each agent's own folder to itself.

## Adding your harness

Topos needs exactly two facts to deliver to a harness:

1. **Which directories it reads** — the user-scope and project-scope folders it loads skills
   from, and the directory whose existence marks it installed.
2. **What fires its refresh** — a session-start hook, a plugin, or a scheduler that can run
   `topos install --quiet`. The sweep self-throttles, so firing often is free.

If you build or maintain an agent, you can make it topos-deliverable with a pull request to
[`topos-sh/topos`](https://github.com/topos-sh/topos) naming those two facts — the registry is
one table row, and a refresh trigger is usually a screenful of code following an existing
pattern. Open an issue with the two facts if you'd rather we write the row.

The table of directories ships inside the binary, and it also refreshes as data: topos
re-downloads the published copy a few times a day, on the same slow rhythm it uses for a GitHub
source, and the next command reads it. So an agent that moves its skills folder reaches installed
machines without anyone waiting for a release. That path only corrects agents already on this
page — a **new** agent still needs a release, because its refresh trigger is code — and topos
ignores a downloaded row naming an agent it doesn't know. Set
`TOPOS_NO_HARNESS_REGISTRY_UPDATE=1` to keep only the table your binary was built with.
