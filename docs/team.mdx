Teammates in, roles set, each group given what it needs — and proof that it all landed.

## Invite people

```bash
topos invite dana@acme.com --yes
topos invite dana@acme.com --channel backend --yes
```

Plain, or with a first destination. Owner-only, and the server needs
[mail configured](/docs/self-host#mail) — Topos Cloud has it. Each address gets a single-use link,
valid 7 days (re-inviting sends a fresh one), offering all three ways in: a browser click, a
paste-block for their agent, and `topos login <invite-url>`. Accepting is bound to the invited
address, mints an account for someone who has none, and makes them a **member** — raise roles
afterwards on the Members page. `--skill` or `--channel` gives them that skill or set from their
first day, credited to you. Nothing lands on their machines until they run `topos login` there.

<Note>
  Agents distribute skills; **they don't manage people**. `topos invite` is the only roster
  command in the CLI — roles, removal, giving a skill to the team, and leaving are browser acts,
  deliberately.
</Note>

## Roles

| Role | Adds |
|---|---|
| **member** | Use skills, publish to open skills, create channels |
| **reviewer** | Approve/reject proposals, roll back, curate curated channels, see the whole fleet |
| **owner** | Invite, set roles, remove people, give skills to everyone, loosen protection, delete, change settings |

The workspace always keeps an owner: the last one can't be demoted, removed, or leave — promote
someone else first.

## Giving people skills

Everything a person's agents receive is something the workspace **gave** them. Three ways to give:

| Way | What it does |
|---|---|
| The **`everyone`** channel | The baseline: assigned to the whole team, and where a new skill lands by default. Whatever is placed there reaches every member with no steps, and it can be neither deleted nor unassigned |
| **Assign to everyone** — owner, on a skill's page or a channel's | Puts it in every member's set; **Remove from everyone** takes the offer back, and copies already on a machine stay until it updates. Both confirm in place, because both reach people |
| **Add to mine** — any member, from **Your skills → Library** | The same kind of assignment, credited to them |

Their **Your skills → Mine** page is the whole answer, grouped by what put each skill there:
Baseline, Channels, Assigned to you, Picked by me. Every row says which, so nobody has to guess why
a skill showed up.

## Opting out is theirs, not yours

Each row on that page has an off switch. Turning a skill off stops it arriving on **all** of that
person's machines; the row stays visible and dimmed, marked *off — still in the team library*, and
turning it back on is one click. Nothing is deleted — copies already on a machine leave at its next
update.

Two things worth knowing as a curator: it is **per skill** (there is no way to switch off a whole
channel — a channel is a set, and a person opts out of the items they don't want), and it
**survives** version bumps, renames, and moves between channels, because the switch is keyed to the
skill itself.

Someone can also switch a skill off on **one machine** with `topos remove <skill> -g`, which says
nothing about their others. And because a decision in the browser and the bytes on a disk are two
different things, the Sessions page tags a copy still sitting on a machine after being switched
off — *turned off* — until that machine reconciles and clears it.

## Channels — "this group needs this set"

A **channel** is a named set of skills. Create one in the browser (**Channels → New channel**) and
fill it on its Skills tab — or at publish time:

```bash
topos publish db-migrations --to backend --yes
```

Then decide how it reaches people. An owner's **Assign to everyone** on the channel page gives it
to the whole team; anyone else can take it with **Add to my skills** on the same page, which
follows them to every machine they log in (**Remove from my skills** gives it back). Or pin it
where the work is:

```bash
topos add @acme/channels/backend
topos add @acme/channels/backend -g
```

Into this repo's `topos.toml` for everyone working in it, or onto this one machine.

Channels reference, they don't own: a skill in three channels is one skill, delivered once. Any
member may curate an open channel; make one curated (reviewers and owners only) with `topos protect
backend --yes`, using the plain channel name.

## Did it land?

**Settings → Sessions** answers "is everyone current — did the rollback reach?" Every logged-in
machine is listed with its per-skill state (current or behind), when it last reported, and a
freshness chip. Machines report when an agent runs, so an idle laptop reads *stale* — unconfirmed,
not wrong. Owners can approve, reject, and remove sessions there; people end their own with
`topos logout`.

## Removing access

- **Remove a member** (owner, Members page): their membership and their logins in this workspace
  end together. Local copies stay theirs — removal stops future delivery; it never deletes files on
  someone's machine.
- **Remove one machine** (owner, Settings → Sessions): ends exactly that login.
- **Leave** (anyone, their own membership): ends all of your own machines' access.

## Policy

**Settings → General**, owner-only — each knob shows who last changed it:

| Setting | Default | What it does |
|---|---|---|
| Review gate | off | Every skill change needs review, unless a skill overrides it |
| Staleness window | 7 days | When a machine reads *stale* on the Sessions page |
| Session approval | off | New logins wait for an owner's approval before anything is delivered |
| Session expiry | none | How long a login lasts before the machine logs in again |
| Export skills | — | Every skill at its current version, as one zip |

## Who can see what

A workspace's skill and channel pages answer **only for signed-in members** — anyone else gets a
plain 404, so a URL can't leak what exists.

The other direction matters more when you're asking someone to log a work laptop in, and it has its
own page: **What the team can see**, linked from Your skills and from Settings → Sessions. It leads
with what a workspace can *never* read — file contents, prompts, repository code, anything
unpublished — then what it does read (which machines, which shared skills by name, which version,
when each last reported), then that reader's own rows as proof. Send people there instead of
reassuring them.

<Warning>
  Don't hand a skill-page URL to someone outside the workspace as their way in — it 404s for them.
  Send an invitation, or the workspace address for `topos login`.
</Warning>
