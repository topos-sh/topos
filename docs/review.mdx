```bash
topos log customer-lookup
topos diff customer-lookup
topos diff customer-lookup <a>..<b>
```

The history with its versions, messages and ids; your local edits against the team's version; any
two versions. A **version** is named by the hash of its exact contents — `customer-lookup@<version>`
means those files and no others — and each skill has one **current** version. Moving it never
deletes anything, so every move can be undone.

## Propose a change

```bash
topos publish customer-lookup --propose -m "Cover the v2 endpoints" --yes
```

On a `reviewed` skill you don't even need `--propose` — a member's publish becomes a proposal by
itself.

## Review it

```bash
topos review
topos review customer-lookup@<version>
topos review customer-lookup@<version> --approve
topos review customer-lookup@<version> --reject -m "needs a test"
topos review customer-lookup@<version> --withdraw
```

Your inbox, then one proposal read in full. The verdict flag *is* the apply — there is no `--yes`
here.

| Verdict | Who | Effect |
|---|---|---|
| `--approve` | reviewer or owner | Ships it — the whole team is on it at their next update |
| `--reject` | reviewer or owner | Declines it; the `-m` reason goes back to the author |
| `--withdraw` | the author | Retracts your own open proposal |

Approval is trustworthy by construction: what ships is exactly what you reviewed (if the skill
moved meanwhile, the approval refuses and you look again); the content hash is re-checked end to
end; and on a `reviewed` skill you can never approve your own proposal — a second person must. The
same review lives in the browser, on each skill's **Proposals** tab: rendered diffs, comments,
Approve/Reject.

## Require review

```bash
topos protect customer-lookup --yes
topos protect customer-lookup open --yes
```

Review required, then back to direct publishing (owners). There is also a workspace-wide default:
the **Review gate** switch on Settings → General. Protect the skills many people rely on; a
two-person utility usually doesn't need it.

## Roll back

```bash
topos revert customer-lookup --to <version> --yes
topos update customer-lookup@<version>
```

The first moves the **team** back, the second only this machine.

<Warning>
  `--to` names the version you are going back **to** — the good one, not the bad one. Find
  it with `topos log customer-lookup`; a unique prefix of 8+ characters works.
</Warning>

A revert records a new version whose contents are the old one's — history stays complete, and a
revert can itself be reverted. It takes a reviewer or owner; a member's revert is refused, not
turned into a proposal. In the browser: **Roll back** on the skill's History tab.

Like every command, `revert` acts where you stand: inside a checkout it names the copy that
checkout delivers, and once the team has moved it updates that copy the way `topos update
<skill>` would (a copy with unpublished edits gets the same merge handling) and moves the
checkout's `topos.lock` — commit it. `topos revert -g <skill> --to <version>` names your
machine-wide copy instead. Everyone else picks the restored version up at their next update.

## Your edits are safe

Editing a delivered skill creates a **draft**: an update never overwrites unpublished edits — it
merges the team's changes around them. A copy you have not edited follows the team, the way a clean
checkout does; when an update replaces it with a version that undoes one you published (a revert,
say), the receipt says which version it replaced and how to bring it back. A published version can
always be brought back: `topos revert <skill> --to <version>`.

If the same skill sits in several of your agents' directories, edit **one** of them. Once your edit
has settled — unchanged since the previous check — the next update copies it onto the skill's other
copies in the same scope and says so on the receipt.

When the team's changes and yours genuinely collide, your agents' folders are left exactly as they
were: still your version, never conflict markers — nothing an agent could read mid-merge and act
on. A copy of both versions, marked up for a by-hand merge, goes to Topos's own folder instead
(`~/.topos/conflicts/<skill>/`, or `<project>/.topos/state/<you>/conflicts/<skill>/` for a skill a
project asks for). The receipt names that folder and both ways out, and publishing that skill is
blocked until you take one:

```bash
topos diff customer-lookup
topos update customer-lookup --keep-mine
topos update customer-lookup --reset --yes
```

See your side; commit the merge you made in that folder — or, by leaving the folder alone, keep
**your** wording on the lines you both changed; or take the **team's** version instead, dropping
yours.

Keeping your version is exactly what it sounds like, and no more than that: your wording wins the
lines the two of you both rewrote, and everything else they changed comes in — a file only they
touched, a paragraph nowhere near yours, a file they added. The receipt names the files the rest
came in on, the contested one included: your wording won those lines, and their other changes to
that same file still landed. It is the same thing you would get by pulling their change, editing the
contested lines back to your wording, and committing.

Committing a merge you made by hand is the other half, and the receipt says so plainly — it landed
what you left in the folder, exactly as you left it. Nothing there is topos's choice, so it claims
nothing about whose wording won.

From there it is a normal draft: `topos diff` shows it, `topos update` keeps merging their later
changes into it, and `topos publish` ships it like any other change.

`--keep-mine` only finishes a merge that has actually stopped. Run it when nothing is waiting and it
says so and points you at `topos update <skill>` — the ordinary update, which takes their changes
and stops only where the two of you really collide.

## When two copies disagree

Edit the same skill in two folders and the copies stop agreeing on what the draft is. Nothing is
overwritten — topos stops and asks which one you mean, listing every copy with what you can do
with it. Answer with `--dest <folder>` (or `-a <agent>`) on any of the three verbs:

```bash
topos diff coolify-deploy --dest .claude/skills
topos publish coolify-deploy --dest .agents/skills --yes
topos update coolify-deploy --dest .claude/skills --reset --yes
```

The folder is written however topos last printed it at you: the one the `topos.toml` line names
(`.claude/skills`), the one `topos list` prints (`project/.claude/skills/coolify-deploy`), or an
absolute path. Publishing or dropping one copy leaves every other copy exactly as it is. With two
copies that ends it: the survivor becomes your single ordinary draft. With three or more, repeat
until one is left. `topos update <skill> --reset` with no folder still drops **every** copy's edits
at once.

`--dest` on `diff` narrows only your side; it always compares against the version you last applied,
so two runs answer the same question about two folders.

## Leaked a secret?

A revert doesn't help — old versions remain fetchable from history. In order:

1. **Publish a scrubbed version.** Every machine replaces the leaked files at its next update —
   the fastest-acting step.
2. **Rotate the credential.** The real security action. Assume the secret escaped.
3. **Watch Settings → Sessions.** It lists exactly which machines still hold old versions — chase
   the stragglers by hand.
4. **Purge the poisoned versions.** Owner-only, in the browser: the contents are dropped from
   history. Machines that already fetched them are listed, never silently forgotten.
