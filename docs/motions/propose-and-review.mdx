This is the flywheel. Someone improves a shared skill while working; the improvement comes back as a
reviewable change instead of drifting into a private fork.

## Open a proposal

```bash
topos diff pr-describe                                   # see your draft
topos publish pr-describe --propose -m "Cover stacked PRs" --yes
```

On a `reviewed` skill you do not need `--propose` — an ordinary publish is rerouted into a proposal
and the receipt says so. Use `--propose` when you *want* review on an open skill.

A proposal is not a special object: **a proposal is a version that `current` has not moved to.** Its
`@<hash>` is how you name it.

## The inbox

```bash
topos review
```

Lists open proposals across every workspace you are in, split into what is yours and what awaits
you, each entry led by its author's message.

## Look at one

```bash
topos review pr-describe@9f2c1a8b     # describe: author, message, base, the diff vs current
topos diff pr-describe @9f2c1a8b      # just the diff
```

The describe flags the case where `current` has moved since the proposal was written.

<Note>
  Under `--json` the diff body is capped at 64 KiB by default, truncated at file boundaries, with
  `patch_omitted` marks and a `FETCH_FULL_DIFF` next action carrying the exact command to get the
  rest. Pass `--max-bytes 0` for no cap.
</Note>

## Land a verdict

```bash
topos review pr-describe@9f2c1a8b --approve
topos review pr-describe@9f2c1a8b --reject -m "needs a test"
topos review pr-describe@9f2c1a8b --withdraw
```

| Flag | Who | Effect |
|---|---|---|
| `--approve` | reviewer or owner | Moves `current` to the candidate |
| `--reject` | reviewer or owner | Declines it; `-m <reason>` is **required** and goes back to the author |
| `--withdraw` | the author | Retracts your own open proposal |

<Warning>
  **`--yes` is not meaningful on `review`** — the verdict flag *is* the apply. A target with no
  verdict is the describe. Passing two verdict flags is a usage error (exit 2).
</Warning>

### Approval is bound to what you reviewed

`--approve` is a compare-and-set against the base the diff was computed on. If `current` moved while
you were reading, the approval is **refused** and you look again — so what lands is exactly what was
reviewed, never something unseen.

The reviewer also binds the proposal's recorded identity: the bundle digest is re-derived from the
fetched bytes and must reproduce the proposal's hash. A tampered server cannot get a reviewer to sign
over forged bytes.

## Reviewing in the browser

Each skill has a **Proposals** tab, with open proposals first and then the resolved record — who
decided, and on a rejection, why.

The review page shows the author and message, a **trust panel** with the byte-exact digest, a file
summary, and rendered diffs. Then:

- **Approve — make this current** is the primary action, bound to the generation the diff was
  rendered against.
- **Reject** is folded behind a disclosure with a **mandatory** reason (up to 2000 characters), so it
  is never a stray click.
- **Four-eyes:** if you proposed the candidate *and* the effective protection is `reviewed`, Approve
  is replaced by a note that a different owner or reviewer must approve it, and your leg becomes
  **Withdraw**. The server re-checks this.
- **Members** can read and comment; an owner or reviewer decides.
- A **"Prefer the CLI?"** disclosure gives you the copyable approve / diff / reject commands.

If a candidate's bytes have already been reclaimed (the server keeps only current versions and open
proposals), the record still renders — but the decision forms are gone, because the approval binding
*is* the rendered diff.

## What the author sees

The verdict comes back with its reason. Their agent narrates it at the next session: your fix is
live and the whole team has it, or here is why it was declined.

Seeing an improvement propagate is what makes someone share the next one — which is the entire point
of the loop.

## Reviewing well

<AccordionGroup>
  <Accordion title="Ask for intent, not just a diff">
    `-m` is required for a rejection and strongly expected on a publish. A diff without intent is not
    reviewable — if the message does not say why, ask before approving.
  </Accordion>
  <Accordion title="Protection follows audience">
    `topos protect <skill>`'s describe tells you how many people the skill reaches. Widely-reaching
    skills earn `reviewed`; a two-person utility usually does not.
  </Accordion>
  <Accordion title="Rejection is not the only tool">
    A change that is right but risky can land and be reverted in one command. `topos revert` is a
    forward, invertible move — see [Roll back](/motions/roll-back).
  </Accordion>
</AccordionGroup>
