---
title: "Connect a machine"
description: "Log an installation into a workspace, resume a pending approval, and end a session."
icon: "plug"
---

Connecting is one act: `topos login <address>`. It mints a **session** — this installation, logged
into one workspace — and arms the auto-update trigger in your agent harness.

## Log in

```bash
topos login https://topos.sh/acme
```

Every one of these addresses is accepted, and the shape alone decides the meaning — no network call
is needed to parse what you typed:

| You type | Means |
|---|---|
| `acme` | The workspace `acme` on the default server |
| `topos.sh/acme` | Explicit server and workspace |
| `https://topos.sh/acme` | The same, pasted from the browser |
| `https://topos.example.com` | A self-hosted origin — "the workspace that origin addresses" |
| `https://topos.sh/acme/invite/<token>` | Straight from the invitation mail |
| *(nothing)* | Resume a pending approval |

Then approve in a browser:

```
Logging into 'acme'.
Approve this login in your browser:
  Open: https://topos.sh/verify?...
  Code: ABCD-1234 (the page shows the same code — confirm it matches)
Then re-run `topos login` to finish.
```

Where a browser is plausible, Topos takes a different route entirely: it binds an ephemeral
`127.0.0.1` listener *before* starting the flow and opens the approval page itself, so there is
nothing to type.

<Note>
  In that codeless mode the approval redirect **carries the authorization code** — the second of the
  two secrets the exchange needs. So the hand-off is not an advisory wake-up: only a browser on
  **this** machine can deliver it, which is what makes a forwarded approve-link useless to whoever
  sent it. Approving mints nothing on its own; the session is created at the exchange, once both
  secrets are present.

  The practical consequence: if that hand-off is lost, the login cannot complete. Re-running
  `topos login` tells you so and clears the pending flow, rather than polling something that can
  never answer.
</Note>

A successful login prints what connecting delivers:

```
Logged into Acme (acme) — your profile delivers 3 skills here
(deploy, code-review, release-notes); updates arrive silently (`topos update` any time).
Undo: topos logout acme
```

<Note>
  **Login is the acceptance.** From here on delivery is silent. There is no per-bundle prompt and no
  per-version confirmation for workspace content.
</Note>

## Automation-safe behavior

<Tabs>
  <Tab title="From a terminal">
    Blocks until you approve or the code expires. A browser opens automatically where one is
    plausible.

    ```bash
    topos login topos.sh/acme
    ```
  </Tab>
  <Tab title="From a script or agent">
    A piped run **never blocks**: it prints the approval URL, polls once, and exits `0`. Re-run to
    poll again.

    ```bash
    topos login topos.sh/acme --json
    topos login --json          # poll again
    ```

    To block deliberately, ask for it — and cap it:

    ```bash
    topos login topos.sh/acme --wait 120
    ```
  </Tab>
  <Tab title="Headless / SSH">
    No browser is opened when `SSH_CONNECTION` or `SSH_TTY` is set, or when `TOPOS_NO_BROWSER` is set.
    You get the printed URL and typed code — approve it from any browser.

    ```bash
    TOPOS_NO_BROWSER=1 topos login topos.sh/acme --wait
    ```
  </Tab>
</Tabs>

<Warning>
  A `--json` login never opens a browser and never blocks. If you are writing agent instructions,
  say: run it, show the human the URL, then re-run to poll. **The agent cannot approve on the human's
  behalf** — that is the point of the ceremony.
</Warning>

## Approving

The approval page is `<origin>/verify`. It shows the machine's name and its code and asks you to
confirm the code matches your terminal before approving. It states which workspace the login is for,
and it is a plain signed-in accept — no password re-entry.

If the workspace has **session approval** turned on, a member's new session is born `pending` and
waits for an owner to approve it on the sessions page. Nothing is delivered while it is pending, and
the login receipt says so.

## More workspaces

Each workspace is its own login on the same installation:

```bash
topos login topos.sh/acme
topos login topos.sh/beta
topos status              # both sessions listed
```

A project's `topos.toml` may reference bundles from several workspaces; each resolves through its
matching session. Missing one, you get everything else plus one honest line.

## Check where you stand

```bash
topos status        # offline: sessions, resolved skills, trigger state, version
topos auth status   # per-session access health, hook health, reporting posture
```

`status` is guaranteed offline and read-only — it dials nothing and repairs nothing.

## Log out

```bash
topos logout acme      # one workspace, named positionally
topos logout           # inferred when there is only one session
topos logout --all     # every session on this installation
```

<Warning>
  `logout` takes the workspace **positionally**. The global `--workspace` flag does not apply here
  and is a usage error (exit 2). This argument is currently missing from the generated command
  reference; `topos logout --help` shows it correctly.
</Warning>

Logging out revokes the session server-side and then signs out locally — the local sign-out proceeds
regardless, and the receipt reports the server outcome honestly.

**Skills, drafts, and manifests stay put.** `topos login <address>` signs back in and delivery
resumes.

## Removing Topos entirely

```bash
topos uninstall          # describe: which hook files, which sidecar paths
topos uninstall --yes    # apply
```

This scrubs the auto-update triggers from your harness configs and deletes the `~/.topos/` sidecar
tree, which is where the session credential lives.

**It never deletes a skill byte** — the files in your agent directories are left untouched. The
`topos` binary is not self-deleted either; its path is printed so you can remove it with whatever
installed it.
