# Topos documentation

The source for the official Topos documentation, served by the product web app itself at
**[topos.sh/docs](https://topos.sh/docs)** — and by every self-hosted server at
`<origin>/docs`. The content is plain MDX, so it is also readable straight from this repository.

```
docs/
├── nav.json          # the ordered sidebar — the single source of navigation
├── index.mdx         # the docs home
├── quickstart.mdx  install.mdx  add.mdx  publish.mdx  review.mdx
├── team.mdx  agents.mdx  harnesses.mdx  self-host.mdx
├── cli.mdx           # a thin page; its body is the generated reference (see below)
├── cli.md            # GENERATED by `cargo xtask gen-cli-ref` — never hand-edit
└── README.md         # this file
```

Every page is also served as plain markdown at its URL + `.md`, and the machine index is
`/docs/llms.txt` — both rendered by the app, no extra step.

## Adding or editing a page

A page is one `.mdx` file at the root of `docs/`. Its id is the filename without the extension,
its URL is `/docs/<id>`, and it must appear exactly once in `nav.json`:

```json
[
  { "group": "Start here", "pages": ["index", "quickstart", "install"] }
]
```

### Frontmatter — exactly these keys

```yaml
---
title: Publish a skill              # required — the h1 and the <title>
description: One sentence.          # required — meta description and index text
sidebar_label: Publish              # optional — a short label for the nav
---
```

### Components — the complete set

Everything else is plain markdown. These are the only components the renderer implements:

| Component | Use for |
|---|---|
| `<Note>` | an aside worth reading, not a hazard |
| `<Warning>` | a real hazard: data loss, unintended reach, irreversibility |
| `<Tip>` | an optional shortcut |
| `<Steps>` + `<Step title="…">` | an ordered procedure |
| `<Tabs>` + `<Tab title="…">` | the same task done two ways |
| `<Card title="…" href="…">`, optionally in `<CardGrid>` | a small set of next destinations |
| `<Cta title="…" href="…" />` | ONE button-styled link — the page's primary action |
| `<Columns>` + `<Column title="…">` | two labelled blocks side by side (e.g. terminal vs agent) |

Fenced code blocks take a language and an optional title:
` ```bash title="Terminal" `. Command fences (`bash`/`sh`/`console`) render on the dark
terminal surface; every block gets a copy button automatically.

Two MDX gotchas: angle-bracket placeholders like `<skill>` must live inside code spans or fences,
never in bare prose (MDX parses them as components), and internal links are written absolute with
the prefix — `/docs/add`, never a relative path.

### After editing, regenerate

These files are compiled at build time into one committed module the app imports, so the runtime
reads nothing from disk. Any edit under `docs/` needs a regenerate, in the same commit:

```sh
cd web && bun run gen:docs
```

`bun run check` runs `check:docs`, which recompiles in memory and fails on drift — so a content
edit without a regenerate turns CI red rather than shipping a stale page. An unknown component, an
unclosed tag, a missing frontmatter key, or a page missing from `nav.json` fails the generate
loudly, naming the file.

## The generated CLI reference

`docs/cli.md` is rendered from the real clap command tree by `cargo xtask gen-cli-ref` (the
`--check` variant is the CI drift gate) and is byte-identical to the built-in skill's copy at
`skills/topos/reference.md`. It is referenced from Rust source and a test — **never hand-edit
it, and never move it.**

`docs/cli.mdx` is the site page: frontmatter, a short intro, and one marker line —

```
{/* GENERATED-CLI-REFERENCE */}
```

— which the renderer expands with the body of `docs/cli.md` at build time (minus the file's own
H1 and provenance quote — the page provides both). After changing the CLI, run
`cargo xtask gen-cli-ref` and commit the regenerated `cli.md`; the page needs no edit.

## Writing conventions

- **Say what is true today, including gaps.** Where something is not built or is a known rough
  edge, name it in a `<Note>` or `<Warning>` rather than implying it works.
- **The code is the authority.** If a page and the code disagree, the code is right and the page
  gets fixed in the same change. Verify commands and output against the CLI and web app before
  publishing them.
- **Explain with examples.** Concepts are introduced inside the motion that needs them — one or
  two sentences, then the command. No standalone concept pages.
- **The command is the star; output is not.** Lead with what to run, then say what happens in
  one plain sentence. Do not paste CLI output — it dates fast, buries the command, and the
  reader's own terminal will show it anyway. The one exception is output that IS the interface
  (the `--json` envelope on the agents page). Placeholders are marked `<like-this>` inside code.
- **Write for someone who has never seen Topos.** Product words only (the vocabulary below) —
  never internal design vocabulary, and never a concept the reader can't act on.
- **Written for people AND agents.** Commands copy-pasteable and complete, tables parseable,
  explicit over clever.
- **Vocabulary**: workspace · seat · session · manifest · profile · channel · skill · version ·
  `current` · draft · proposal · auto-update. Not: device, follow/unfollow, or "currency" (an
  internal code spelling, never a product word).
- **Compression is a feature.** This is deliberately a small set of pages (~12). Deepen an
  existing page before adding a new one.

## What lives here and what does not

`docs/` is the published documentation. Maintainer runbooks do not belong here — the release
runbook is `RELEASING.md` at the repository root, contributor guidance is `CONTRIBUTING.md`, and
the design doc is `ARCHITECTURE.md`.
