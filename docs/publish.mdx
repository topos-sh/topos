```bash
topos publish pr-describe
topos publish pr-describe --yes
```

The bare run is a preview — it names the channel the skill lands in, whether review is required,
and the exact apply command, and changes nothing. `--yes` applies it, as a new skill or as a new
version of one already shared. What you point it at:

| Target | Meaning |
|---|---|
| `pr-describe` | A skill Topos already manages |
| `./tools/pr-describe` | Any folder with a `SKILL.md` — adopted, then published |
| `pr-describe@<version>` | Pinned — refuses if the files changed since you looked |

## Your first publish

```bash
topos publish ~/.claude/skills/pr-describe --yes
```

That is all a brand-new workspace needs. The skill gets one identity, one version history, and a
page at `https://topos.sh/acme/skills/pr-describe`; teammates' machines receive it through the
`everyone` channel automatically.

Publishing also flips who leads: the workspace's current version now decides what everyone gets —
including you. Your local copy stays where it is and updates with the team; your future edits are
drafts you can publish again. (One exception: a skill imported from GitHub keeps following its
pinned source — the receipt says so.)

## Say what changed

```bash
topos publish pr-describe -m "Cover stacked PRs" --yes
```

`-m` becomes the version's history line — what a reviewer reads first, and what a teammate's agent
can narrate when the update arrives. A diff without intent is hard to review; write one.

## Pick a channel

```bash
topos publish db-migrations --to backend --yes
```

A new skill with no `--to` lands in **`everyone`** and reaches the whole team. `--to` places it
into a narrower channel instead — the channel must already exist (create channels in the browser).
Under a **curated** channel your publish lands in the catalog and a curator places it; the receipt
says so.

## When review is on

| The skill is | A member's publish |
|---|---|
| `open` (default) | Ships immediately |
| `reviewed` | Opens a **proposal** — nothing changes until a reviewer approves |

You are never blocked for publishing to a `reviewed` skill — it becomes a proposal, and the
receipt hands you the review command to pass along. Reviewers and owners ship directly even there;
add `--propose` to ask for review anyway. The very first version of a new skill always ships
directly — there is nothing to compare it against yet.

The other half of the loop: [Review, protect, roll back](/docs/review).

## Publishing an MCP server

```bash
topos add --mcp ./tools/weather
topos publish weather --yes
```

A folder whose one file is a `server.json` publishes exactly like a skill — same preview, same
`--to`, same review gate. The receipt says the workspace recorded it as an `mcp` bundle, which is
what tells every receiving machine to place it as a server entry in each agent's own config rather
than as a skill folder.

The document is re-checked against the same gate the browser import runs, **before** anything is
sent: no local `packages[]`, one `streamable-http` endpoint over `https`, no `{placeholder}` in the
URL, and no credential in any form — including a header with no literal value, or a literal that
merely has the shape of a token. A refusal names its own code and lands nothing.
[The full list](/docs/mcp#what-topos-refuses-and-why). One extra check belongs to the workspace: the
document's own registry name must be free here, since that is the name the workspace's registry lane
resolves by.

<Note>
  Governance transfers, the entry name does not. The config entry on the machine that authored the
  folder keeps the key it was minted under, because several agents file an OAuth sign-in against
  that name — a rename would strand it. Teammates, meeting the server for the first time through
  the workspace, get `topos-<workspace>-<name>`.
</Note>

## If it refuses

| Refusal | Fix |
|---|---|
| Nothing changed | There is no new version to ship |
| Your copy is behind the team | `topos update <skill>`, then publish again |
| `--to` names the workspace | `--to` takes a **channel**: `--to backend` |
| No such channel | Create it in the browser first |
| Not logged in | `topos login <workspace-address>` |

Every publish is safe to retry — an interrupted one resumes exactly, never doubles.
