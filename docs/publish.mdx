```bash
topos publish pr-describe
topos publish pr-describe --yes
```

The bare run is a preview — it counts what changes, names the channel the skill lands in and
whether review is required, and hands you the exact apply command; it changes nothing. `--yes`
applies it, as a new skill or as a new version of one already shared. What you point it at:

| Target | Meaning |
|---|---|
| `pr-describe` | A skill Topos already manages |
| `./tools/pr-describe` | Any folder with a `SKILL.md` — adopted, then published |
| `pr-describe@<version>` | Pinned — refuses if the files changed since you looked |

## Your first publish

```bash
topos publish ~/.claude/skills/pr-describe --yes
```

That is all a brand-new workspace needs. The skill gets one identity, one version history, and a
page at `https://topos.sh/acme/skills/pr-describe`; teammates' machines receive it through the
`everyone` channel automatically.

Publishing also flips who leads: the workspace's current version now decides what everyone gets —
including you. Your local copy stays where it is and updates with the team; your future edits are
drafts you can publish again. (One exception: a skill imported from GitHub keeps following its
pinned source — the receipt says so.)

## Say what changed

```bash
topos publish pr-describe -m "Cover stacked PRs" --yes
```

`-m` becomes the version's history line — what a reviewer reads first, and what a teammate's agent
can narrate when the update arrives. A diff without intent is hard to review; write one.

## Pick a channel

```bash
topos publish db-migrations --to backend --yes
```

A new skill with no `--to` lands in **`everyone`** and reaches the whole team. `--to` places it
into a narrower channel instead — the channel must already exist (create channels in the browser).
Under a **curated** channel your publish lands in the catalog and a curator places it; the receipt
says so.

## When review is on

| The skill is | A member's publish |
|---|---|
| `open` (default) | Ships immediately |
| `reviewed` | Opens a **proposal** — nothing changes until a reviewer approves |

You are never blocked for publishing to a `reviewed` skill — it becomes a proposal, and the
receipt hands you the review command to pass along. Reviewers and owners ship directly even there;
add `--propose` to ask for review anyway. The very first version of a new skill always ships
directly — there is nothing to compare it against yet.

The other half of the loop: [Review, protect, roll back](/docs/review).

## MCP servers are not published

```bash
topos add --kind mcp io.github.acme/weather
```

`publish` ships a folder's files, and an MCP server has none: it is a catalog entry your workspace
connects to, or one your workspace wrote down. So `topos publish` over one is refused, and the way
to share a server is the `add` above — the name (or a link to its `server.json`) goes to your
workspace, which reads the document, rules on it, and shares it under a name every machine adds it
by. Updates come from the catalog, or from the server's own page for one your workspace holds:
[MCP servers](/docs/mcp).

## If you have it in two places

A skill can sit both in a project checkout and machine-wide, each with its own draft. A bare
publish ships the copy you are standing in when it has edits, and the other one when that is where
the edits are — the preview and the receipt name the folder whenever it is not the one you stand
in. `-g` names your machine-wide copy outright. When both copies have edits, the one you stand in
ships and the other is named with what it takes to share it too: after a landed publish that copy
is behind the version that just landed, so the receipt names the update and the publish, in that
order. A proposal moves nothing, so there the other copy is still one publish away.

```bash
topos publish pr-describe -g --yes    # the machine-wide copy, from inside a checkout
```

Publishing a copy that already matches the published version is not an error — it says
`already published — your copy matches current` and stops. If the edits are in your other copy, it
says which command shares them.

"Current" is what the workspace serves, read fresh on every publish and every `topos diff` — never
what this machine last saw. So if your copy equals an older version than current (you published,
then someone reverted, say), it is not "already published": the preview says which version current
is and that `--yes` will publish your copy's content forward as a new version on top of it; the
receipt names the version that landed (the preview does not guess it — `-m` is part of the id).
Re-publishing older content is an ordinary act; `topos log` keeps every hop, and the receipt's
`undo:` line puts the team back.

## The checkout's lock follows

A publish run inside a checkout moves that checkout's `topos.lock` entry to the version that
just landed — a commit moves `HEAD` — and the receipt asks you to commit the file. Nothing else
in the repo changes; a row your `topos.toml` pins is left at its pin, and the receipt says so.
See [topos.toml and topos.lock](/docs/topos-toml).

## If it refuses

| Refusal | Fix |
|---|---|
| Your copy has edits and the team published a newer version since | `topos update <skill>` merges theirs into yours — nothing of yours is overwritten — then publish again. (A copy you did not edit is never refused for being older: it publishes forward, and the preview names the version it lands on.) |
| `--to` names the workspace | `--to` takes a **channel**: `--to backend` |
| No such channel | Create it in the browser first |
| Not logged in | `topos login <workspace-address>` |

Every publish is safe to retry — an interrupted one resumes exactly, never doubles.
