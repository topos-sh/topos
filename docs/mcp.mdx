A workspace shares two kinds of bundle. A **skill** is a folder of instructions your agent reads;
an **MCP server** is one file naming a server your agents can call as tools. Both are published
once, given to people the same way, and updated the same way — what differs is where the bytes
land. A skill lands in a skills directory; an MCP server lands as one entry in each agent's own MCP
config.

## What an MCP bundle is

One file, `server.json`, in the format the
[official MCP registry](https://registry.modelcontextprotocol.io) serves — the same document that
registry hands out, unchanged. (A `README.md` may sit beside it; nothing else may — any other file
refuses at publish, and both files' bytes run the same credential scan.) Three constraints decide
everything else on this page:

- **Something to run.** The document offers a `streamable-http` endpoint over `https`, or one or
  more packages, or both. A document offering neither has nothing to hand an agent and refuses.
- **Pinned.** Every package names exactly one immutable thing: an exact version for npm and PyPI, an
  `@sha256:` digest for a container image, a file hash for an `.mcpb` download. A version range, a
  dist-tag, `latest`, or an image tag refuses — a tag is a label the publisher can move to other
  bytes, and "the same bytes everywhere" is the promise that breaks.
- **Secretless.** The document carries no credential and no slot for one *in what travels*. Where a
  server needs a sign-in, that sign-in is your agent's own OAuth dance on your own machine — Topos
  never sees it, never stores it, and never moves it between machines. A package may *name* the
  environment variable it wants (`GITHUB_TOKEN`, and `isSecret` on it is fine): the machine that
  runs the server fills that in. What refuses is such a slot arriving with the value already in it.

```json title="server.json — the whole bundle"
{
  "name": "io.github.acme/weather",
  "description": "Current conditions and forecasts for a named place.",
  "version": "1.4.0",
  "remotes": [
    {
      "type": "streamable-http",
      "url": "https://weather.acme.example/mcp",
      "headers": [{ "name": "X-Region", "value": "eu-west-1" }]
    }
  ],
  "_meta": { "sh.topos/auth": "oauth" }
}
```

Headers on a remote are allowed when their values are **literal** — every machine sends the same
bytes, so nothing is filled in per person. `_meta."sh.topos/auth"` is optional and says what someone
is signing up for: `oauth` (an agent will be asked to authorize on first use) or `none` (the
publisher states no credential is needed). Saying nothing is not a claim that none is needed, and
Topos never reads silence as one.

Which registries a package may come from is the format's question, not Topos's: `npm`, `pypi`,
`oci`, `nuget`, `mcpb` and whatever the registry adds next all publish here. Whether a given machine
can set a particular one up is answered **on that machine**, in plain words, when the entry is
written — not by refusing the document for everyone.

## Three ways in

<Tabs>
  <Tab title="The browser">
    The left panel carries an **MCP servers** section of its own, next to Skills; its `+` (and
    **Add an MCP server** on the dashboard) opens `<origin>/mcp/new`. The page opens on
    a searchable grid of popular servers — Linear, Notion, GitHub, Sentry, Figma and the rest —
    each showing what it connects to and whether a sign-in is coming. Click one and it asks,
    there and then, whether to add it: the endpoint, the auth, the exact `server.json` bytes,
    and the name it will take. Cancel or press Escape and nothing has happened; confirm and it
    publishes.

    Adding a server puts it in the workspace and nowhere else — it reaches no machines until it
    is in a channel. **Share into** offers that on the way in, and it rests on *no channel*;
    a channel can just as well be chosen later, on the channel's own page.

    Anything not on that list goes in under **Custom server**, which is the same three typed
    sources as ever: the MCP registry by name, a URL to a `server.json`, or the document pasted
    in. Those three are read by the server first and shown as a preview, because nobody here has
    seen those bytes yet. Every one of them — a pick included — passes the same gate; the list
    only saves the typing.

    <Note>
      A URL is fetched by the server your workspace runs on: `https` only, redirects refused, and
      only addresses on the public internet. Pasting and picking from the list are the two paths
      that make no outbound request at all — pasting is what a server inside your own network
      wants.
    </Note>
  </Tab>
  <Tab title="The CLI">
    ```bash
    topos add weather                   # a server your workspace already publishes
    topos add --kind mcp ./tools/weather   # a folder on this machine holding a server.json
    ```

    Those are the two doors. A workspace bundle needs no flag — the catalog already records what
    each bundle is, so `topos add weather` (or `topos add @acme/weather`) gets the server with its
    kind intact. A local folder needs `--kind mcp`, because a folder is just a folder until
    somebody says what it holds.

    The CLI fetches nothing. A registry name or a link to a `server.json` is refused, pointing at
    the page above: the server goes into the workspace once, where the whole team reviews,
    reverts, and stays current on one governed copy, instead of each machine resolving a pointer
    for itself.

    Both doors apply immediately, and the receipt **leads with the undo**: what the server is, the
    endpoint it points at, whether a sign-in is coming, which agents it reached — and the one
    `topos remove` that takes it back. A folder on your disk is adopted in place, so `remove`
    drops its row and never deletes your folder.
  </Tab>
  <Tab title="Publish a folder">
    ```bash
    topos add --kind mcp ./tools/weather
    topos publish weather --yes
    ```

    Author the document in a folder, add it, then publish — the same two steps as a skill.
    Publishing transfers governance: the `./tools/weather` line becomes the workspace reference,
    and from then on everyone (including you) gets the workspace's current version.
  </Tab>
</Tabs>

Each `add` records **one line** in the nearest [`topos.toml`](/docs/topos-toml) at or above this
folder — or your machine's own file with `-g` — and converges your agents' configs in the same
command. An adopted folder is left exactly where it is, so the row points at bytes you can read and
commit.

`--kind mcp` describes a *folder*, never a workspace bundle. Say it when a folder holding a
`server.json` would otherwise be adopted as a skill; `--kind skill` on that same folder adopts it as
a skill, because an explicit word is yours to give.

Published servers live under their own addresses — `<origin>/mcp/<name>`, listed in the **MCP
servers** section of the panel and of the dashboard. Nothing about a server is filed under skills.
(An install *is* its workspace, so every path on this page is origin-rooted; a deployment hosting
several workspaces nests all of them under `/<workspace>`.)

## How delivery works

Exactly like a skill. An MCP server sits in the catalog, goes into the `everyone` channel or a
narrower one, is assigned to people or picked by them, and reaches every machine they log in — no
per-machine setup, no second step. What is different is the destination:

- **No skill folder.** An MCP bundle is never placed in a skills directory. Its bytes stay in
  Topos's own store; what your agents see is one config entry each.
- **One entry per detected agent**, under a stable key: `topos-<workspace>-<name>` for a workspace
  bundle, `topos-local-<name>` for a row naming a folder.

```json title="~/.cursor/mcp.json — what lands"
{
  "mcpServers": {
    "topos-acme-weather": {
      "headers": { "X-Region": "eu-west-1" },
      "url": "https://weather.acme.example/mcp"
    }
  }
}
```

The key is minted once and **never changes**, because several agents file an OAuth sign-in under
the server's name and a rename would strand it. That is also why publishing a local folder does not
re-key anything: the entry keeps the name it was born with on the machine that authored it, while a
teammate's machine — meeting the bundle for the first time through the workspace — mints
`topos-<workspace>-<name>`.

### When the bundle is a package

A document that offers packages instead of (or as well as) an address lands as the **program the
agent runs**, in that agent's own spelling — `npx -y @acme/weather-mcp@1.4.0` for npm,
`uvx acme-weather@1.4.0` for PyPI, always at the version the document pins:

```json title="~/.cursor/mcp.json — a package bundle"
{
  "mcpServers": {
    "topos-acme-weather": {
      "args": ["-y", "@acme/weather-mcp@1.4.0"],
      "command": "npx",
      "env": { "ACME_TOKEN": "${ACME_TOKEN}" }
    }
  }
}
```

An environment slot the document leaves empty is written as a **reference** to a variable of that
name, in the form that agent reads: `${VAR}` for most, `{env:VAR}` for OpenCode, and for Codex a
`env_vars = ["VAR"]` list beside the entry (its `env` map is literal text it hands the server
unchanged). The name travels in the bundle; the value stays on your machine, in your own
environment, and Topos never sees it.

Which of the two forms an agent gets is decided per agent, in this order:

1. the document offers an address and the agent dials addresses itself → **the address**;
2. the agent does **not** dial one → **the address through a bridge**: `npx -y mcp-remote@<pinned>
   <url>`, so a stdio-only agent still reaches the same server (its sign-in runs there too);
3. otherwise → the first package Topos can set up, **npm** before **PyPI**, and only a package the
   agent talks to over its pipes (the format also lets a package listen on an http address once it
   is running, which is neither an address every machine dials nor a program an agent can speak to).

Anything a given machine cannot set up is said in plain words on the receipt and re-decided on the
next update — nothing is half-written:

```
not placed: needs node, which is not on this machine. Install node, then run 'topos update'.
not placed: this bundle is packaged as oci, which this version of topos cannot set up yet.
not placed: this bundle's package serves over streamable-http, which this version of topos cannot set up yet.
```

The choice never depends on what a laptop happens to have installed: a missing runtime is a "not
placed" line, never a quiet fallback to a different package, because the same bundle running
different bytes on different machines is the thing sharing is supposed to prevent.

### When each agent picks it up

Sixteen agents have an MCP config surface. Topos writes into the ones it detects on the machine
(and into a config file that already exists, so removals still reach it), and says nothing about
how you sign in — that stays the agent's own business:

| Agent | Picking up the change | Signing in |
|---|---|---|
| Claude Code | loads next session; `/reload-plugins` reloads live | `/mcp` |
| Claude Desktop | quit completely and reopen | in the app, on first use |
| Cline | picked up automatically | Cline's own, on first use |
| Codex | restart `codex` | `codex mcp login <name>` |
| Cursor | restart Cursor | Cursor's own, on first use |
| Gemini CLI | restart `gemini` | Gemini's own, on first use |
| GitHub Copilot CLI | next `copilot` run | Copilot's own, on first use |
| Goose | restart your goose session | Goose's own, on first use |
| Hermes Agent | `/reload-mcp` in a session, or next session | the entry declares `auth: oauth` |
| LM Studio | automatically, when the file is saved | LM Studio's own, on first use |
| OpenCode | restart `opencode` | automatic on the first `401` |
| OpenClaw | picked up automatically | `openclaw mcp login <name>` |
| Roo Code | picked up automatically | Roo's own, on first use |
| VS Code | restart the server from the MCP view | VS Code's own, on first use |
| Windsurf | press refresh in Cascade's MCP panel | Windsurf's own, on first use |
| Zed | picked up automatically | Zed's own, on first use |

Each agent's exact config file — and the environment variables that move it — is in
[Supported agents](/docs/harnesses#mcp-servers).

Twelve of them dial an address and also run a local program. Four are narrower, and Topos says so
rather than guessing: **Claude Desktop** adds remote servers in the app rather than in this file,
so a shared address reaches it as a local bridge process instead; **Goose**, **Hermes Agent** and
**LM Studio** have a confirmed entry grammar for an address only, so a package bundle reports
`not placed` there rather than being written in a shape nobody has verified.

By default the entry reaches every one of those agents this machine has. On `topos add`,
`-a <agent>` (a slug like `cursor`, repeatable) or `--dest <file>` (a config file from that same
set) narrows the row to exactly the files named, recorded as `dest` on the line — so an agent set
up later changes nothing until the line does. The same two flags on `topos remove` subtract one
file at a time: that entry leaves, the row survives with the rest, and subtracting the last file
removes the row. A file outside the known set refuses, because its format has to be known to edit
it.

## Checking that a server actually works

```bash
topos verify weather
```

Delivery says what your machine *has*. `topos verify` says what the server *does* — right now, from
here. Topos dials the address the bundle names (or runs its package), asks the server for its tools,
and prints one line. Nothing is stored and nothing is installed: it is a live check, run when a
server misbehaves and you want to know whether the problem is the server, the network, or the entry.

There are four answers, and each is also the command's exit code, so a script can branch on it
without reading a word. The sign-in answer comes in two sentences, because "sign-in required" hides
two very different situations:

| What it prints | Exit code | What it means |
|---|---|---|
| `responding (12 tools)` | `0` | The server answered and listed its tools. |
| `sign-in required - healthy; your agent app completes sign-in on first use` | `3` | The server wants a sign-in — which is the *right* answer. Topos holds no credential and never sends one; your agent app signs in the first time it uses the server. |
| `sign-in required - this server accepts only pre-registered clients or tokens; an agent cannot complete sign-in by itself` | `3` | The server wants a sign-in too, but it registers no new clients: somebody creates a personal token, or registers an app with the vendor, before any agent can get in. The server is healthy — the setup is manual, once per person or once per organization. |
| `not reachable: ...` | `4` | Nothing answered, or the server is having trouble right now. The rest of the line says which. |
| `reachable but not answering as an MCP server: ...` | `5` | Something answered at that address, but not as an MCP server — usually a wrong URL, or a redirect that was not followed. |

A refusal — no such bundle, an ambiguous name, a bundle that is a skill — exits `1` like every other
command, because nothing was checked. `-g` checks the server your machine-wide scope holds, even
from inside a project. `--json` adds the address dialed (or the program run), the protocol revision
the server answered on, and the same exit code inside the document — plus, on a sign-in, `sign_in`:
`self_service` or `manual`, and absent where the server's own sign-in documents could not be read
(which is when the first sentence is printed, since an unreadable server is not a manual one).

## Updating a server

```bash
topos publish weather --yes
```

A server is updated from the folder that authored it — the one you adopted with `topos add
--kind mcp ./tools/weather`. Edit its `server.json` — a moved endpoint, a new version string, a
changed header — and publish it.
The document runs the same gate it ran the first time, and on a `reviewed` bundle the publish opens
a [proposal](/docs/review) instead: the approval is what moves `current`. Every machine picks the
new address up on its next update, in place, under the key it already has — so a sign-in already
filed there survives.

An MCP bundle's bytes stay in Topos's store rather than in a directory, so a machine that only
*receives* the server holds no copy to edit. Updates come from the machine the folder is on; keep it
in a repo if more than one person should be able to publish them.

The browser is a way in, not a way to update: each import mints a **new** bundle, so importing a
document whose registry name this workspace already publishes is refused, naming the server that
already holds it and linking to its page. A server that arrived that way has no authoring folder on
anyone's machine, so replacing it means archiving it on its own **Settings** tab — which frees the
registry name — and importing the new document.

## Machine scope and project scope

The two scopes work as they do for skills: your own `~/.topos/topos.toml` (or, with no such file,
what your workspaces give you) follows you, and a repo's committed `topos.toml` governs that
checkout. An MCP row in a project file lands **only in project-level config** — `.mcp.json`,
`.codex/config.toml`, `.cursor/mcp.json`, `.gemini/settings.json`, `.roo/mcp.json`,
`.vscode/mcp.json`, `opencode.json` — and never falls back to your home config, so a committed file
can't quietly reconfigure a contributor's machine.

Those seven files are the whole of it: nine of the sixteen agents have no project-level MCP config
at all — the table in [Supported agents](/docs/harnesses#mcp-servers) marks each of them
`— (none)` — and the receipt that places a project row says so for every one it finds on the
machine, instead of pretending:

```
openclaw: not placed — no project-level config
hermes-agent: not placed — no project-level config
```

Those agents receive the same server through your machine-wide scope. `topos list <name>` names
every agent config that currently holds an entry for the bundle, and an `update` re-decides the
standing facts above from the files each time it runs — so a line stops appearing the moment the
condition behind it does. A project config path that resolves outside the checkout is refused and
named, never redirected.

<Note>
  Codex reads a project `.codex/config.toml` only once you have trusted that repo inside Codex.
  Topos writes the file either way; the trust step is yours.
</Note>

## What Topos refuses, and why

Every refusal is typed, and each one refuses a specific temptation rather than folding into
"invalid". The same rules run in the browser and in the CLI, from the same test vectors.

| Code | Refused | Why |
|---|---|---|
| `MCP_PACKAGE_UNPINNED` | a version range or `latest`; an image with no `@sha256:` digest; an `.mcpb` with no `fileSha256` | the package names a moving target, so two machines installing the same bundle would not get the same bytes |
| `MCP_NO_STREAMABLE_REMOTE` | no `streamable-http` remote (`sse`-only, or none) **and** no packages | there is nothing here for an agent to run |
| `MCP_INSECURE_URL` | a plain `http://` endpoint | every call and every reply would go over the wire in the clear |
| `MCP_URL_TEMPLATE` | a `{placeholder}` in the URL | a template is not an address — someone has to fill it in per machine |
| `MCP_SECRET_REFUSED` | a credential in any form | see below |
| `MCP_INVALID` | not JSON; a missing or malformed `name`, `description`, or `version`; an endpoint that isn't a URL | there is nothing here to publish or point an agent at |
| `MCP_NAME_TAKEN` | a `name` another bundle here already publishes | the registry lane resolves by that name; two claims would make a lookup a coin flip |

`MCP_SECRET_REFUSED` is the widest of them, deliberately. It covers a remote header whose *name*
carries a credential by definition (`Authorization`, `Cookie`, `X-Api-Key` and their kin), a remote
header marked `isSecret`, a remote header with no literal value, a header or endpoint assembled from
per-installation `variables`, a package environment variable or flag named for a credential that
arrives with its value filled in, and a literal value anywhere in the document that simply *has the
shape* of a token —
an API key, a `Bearer` string, a long random-looking run. The scan reads the raw document **before**
any field is read out of it, so a document carrying somebody's token is refused whole, and the
message names the shape it matched, never the value:

```
error: the header X-Api-Key carries a credential by definition — a shared bundle never holds one
```

<Warning>
  A refusal is the whole outcome: nothing is written, nothing is stored, and nothing lands
  half-trusted. If your server genuinely needs a per-person credential, that credential belongs in
  the agent's own sign-in, not in a file the whole team receives.
</Warning>

Two more are reported as warnings rather than refusals, because the rest of the run is still good:
a workspace row whose `dest` names a config file no agent here claims (`MCP_DEST_UNKNOWN` — the
entry is skipped and the known files are listed), and a GitHub-sourced row tagged as an MCP server
(`MCP_GITHUB_UNSUPPORTED`).

## A hand-edited entry is never overwritten

Topos knows exactly which entries it wrote, and it proves it two ways: the key looks managed
(`topos-…`) *and* the entry's contents still match what Topos last wrote there. Edit one of those
entries by hand and it is yours from that moment on:

| What Topos reports | What it means |
|---|---|
| `placed` | this update wrote the entry — placed for the first time, updated, or repaired |
| `current` | already correct; nothing was written |
| `drifted` | you edited it since Topos wrote it — left byte-identical, never touched again |
| `conflicting` | that config key is held by an entry Topos does not own |
| `not-supported` | withheld: no config surface for that agent at this scope |
| `unprovable` | the config file's shape can't be proven safe to edit, so nothing was written |

An update prints the drift next to the skill it belongs to (`cursor: hand-edited — left in
place`), and your workspace's **Settings → Sessions** page carries the same per-agent state as a
chip on every reported machine — so you can see that a rollout landed, and where it didn't.

Everything else about the write is conservative: comments and formatting in a config file you own
are preserved, an unrelated server entry is never disturbed, and applying the same set twice leaves
the file byte-identical.

### Handing one back

Drift lasts until you end it, and ending it is one deletion:

```bash
topos update
```

Delete the entry from the agent's config first, then run that. The key is absent again, so the next
converge writes the current document fresh and the entry is Topos's from then on — every later
change reaches it. Editing the entry back by hand works too, but only if you land on the exact bytes
Topos last wrote; deleting it is the reliable spelling. Until you do, updates to that server stop at
that entry — and every update says so, on the line naming the agent.

## Removing one

```bash
topos remove weather
topos remove weather -g
```

The same inverse as a skill, and the receipt names every config file it touched. Entries you
hand-edited are left in place and disclosed rather than removed. A config file that Topos created
and still wholly owns is deleted when its last entry leaves; a file with anything else in it keeps
everything else.

When a workspace stops giving you an MCP server — unassigned, a channel dropped, access removed —
the entries leave at that machine's next update, the same way a skill's folder does.

## Pointing a registry-aware tool at your workspace

A workspace serves its own MCP servers in the registry's read format, so a tool that already speaks
to a registry can be pointed at Topos instead and get the servers your team curates:

```
GET <origin>/registry/v0.1/servers
GET <origin>/registry/v0.1/servers/<name>/versions
GET <origin>/registry/v0.1/servers/<name>/versions/latest
```

`<name>` is the document's own registry name (`io.github.acme/weather`), so its slash is
percent-encoded into one path segment. The lane answers for **members only** — a browser session or
a machine session's bearer token — and everything else, including a workspace you hold no seat in,
gets the same plain 404. The versions list is deliberately one entry: a workspace publishes a moving
`current`, not a history to pin against. What the team runs is what it serves.
