```bash title="Try it on a laptop"
git clone --depth 1 --branch <release-tag> https://github.com/topos-sh/topos
cd topos
cp .env.example .env      # paste two `openssl rand -hex 32` outputs into the two blank lines
docker compose up -d
```

That is the whole install — take the tag from
[the releases page](https://github.com/topos-sh/topos/releases). Nothing is compiled on the box: the
checkout pins both prebuilt images to that release, alongside the compose file and the database's
first-boot provisioning script, so a clone is one self-consistent deployment and `git status` is
your diff against it. `.env.example` is the whole config surface — every knob, commented, showing
the value already in force — and the two blank lines at its top are the only edits a laptop trial
needs.

Leave either secret blank and `docker compose` refuses to parse the file, naming the variable and
the command that generates one. That happens in your terminal before a single container starts —
there is nothing to dig out of a log.

Then open `http://localhost:3000` **in a browser** — the first browser request is what mints the
workspace and prints the setup link to the logs. Open that link, create the first account, and
connect a machine with `topos login http://localhost:3000`: the CLI accepts an explicit `http://`
address for localhost.

<Note>
  The two secrets ship with no defaults on purpose: a default secret in a public repository is a
  secret everybody has. Compose refuses at parse time while either is missing or empty, and the app
  carries the same refusal at boot — the backstop for deployments that do not come through compose.
</Note>

<Note>
  **Would rather not clone?** `https://topos.sh/compose.yml` and
  `https://topos.sh/compose-init-db.sh` serve the current deployment recipe as two files: fetch the
  second to `scripts/compose-init-db.sh`, where the compose file mounts it into the database's
  first-boot hook, and `chmod +x` it — `curl` cannot carry an execute bit, and without it initdb
  skips the script and the database never reports healthy (deliberately: better to stop than to run
  a database with no application roles in it). Those URLs always serve what is *current* rather than
  a release you chose, so pin `TOPOS_VERSION=vX.Y.Z` in the `.env` you write the two secrets into.
  The same script is also the recipe for [bringing your own Postgres](#bring-your-own-postgres).
</Note>

There is no reduced open-source edition: the CLI, the sharing server, and the entire web app —
sign-in, dashboard, review UI, admin pages, and the API the CLI dials — are all in the
[public repository](https://github.com/topos-sh/topos) under Apache-2.0. A self-hosted install is
**single-tenant**: it *is* one workspace, rooted at your origin, and the address teammates log in
with is simply `https://topos.example.com`.

## What runs

Three services, **one published port**:

| Service | What it is | Published port |
|---|---|---|
| **web** | The whole product app — the only thing that needs to be reachable | `3000` |
| **plane** | Byte custody for skill versions. One caller — the app, over an internal bearer-gated lane | none, deliberately |
| **db** | PostgreSQL 18, digest-pinned. Two roles, two schemas — one per application, boundary enforced by grants | none |

<Warning>
  **`plane` must never be externally reachable.** It publishes no port by design. Do not add
  one, and do not proxy it. The database likewise publishes no port.
</Warning>

### The images

Both application images are published to GHCR, multi-arch (`linux/amd64` and `linux/arm64`), built
by the public repository's release workflow:

| Image | What it is |
|---|---|
| `ghcr.io/topos-sh/topos-web` | The product app — the surface you reach |
| `ghcr.io/topos-sh/topos-plane` | Byte custody, internal-only |

The checkout pins both to the release it was cut for rather than tracking `latest`, and
`TOPOS_VERSION` in your `.env` overrides that without moving the tree. Pinning is deliberate: your
server and your team's CLIs speak one wire, so a server that jumped forward on its own would break
machines you cannot see. Upgrading is a decision you make — see [Upgrades](#upgrades).

Every release publishes an immutable digest and an SBOM per image, and the manifests carry build
provenance you can check against the workflow that produced them (substitute the release you
checked out):

```bash
gh attestation verify oci://ghcr.io/topos-sh/topos-web:vX.Y.Z --repo topos-sh/topos
```

To run a patched tree instead, add the build override beside the compose file — same file, same
topology, images built from your checkout:

```bash
docker compose -f docker-compose.yml -f docker-compose.build.yml up -d --build
```

## A real deployment

<Steps>
  <Step title="Set the five values that must change">
    Fill them into the file you already copied — `cp .env.example .env`, beside
    `docker-compose.yml`. Every line below is in there, commented, with its current value:

    ```bash title=".env"
    # The public origin, behind your reverse proxy. Required.
    TOPOS_PUBLIC_URL=https://topos.example.com

    # The app's session-signing secret — at least 32 characters.
    TOPOS_WEB_AUTH_SECRET=<paste output of: openssl rand -hex 32>

    # The app-to-plane internal bearer. Both services read it; they must match.
    TOPOS_INTERNAL_TOKEN=<paste output of: openssl rand -hex 32>

    # The two database roles' passwords.
    TOPOS_PLANE_DB_PASSWORD=<paste output of: openssl rand -hex 16>
    TOPOS_WEB_DB_PASSWORD=<paste output of: openssl rand -hex 16>

    # Optional: the first workspace's slug. Default: team
    TOPOS_WORKSPACE_NAME=acme
    ```

    Compose does **not** expand `$(…)` in a `.env` file — paste the literals in. The two secrets
    have no defaults to fall back on: blank, and compose refuses to parse. The database passwords
    are not enforced, but change them anyway — on the first `up`, before the volume exists, since
    the roles are created once and a later change only locks the applications out.
  </Step>
  <Step title="Bring it up">
    ```bash
    docker compose up -d
    ```

    Both images are pulled, the database provisions its roles and grants on first boot of a fresh
    volume, and each application migrates its own schema at startup, before serving anything.
  </Step>
  <Step title="Terminate TLS at your proxy">
    Forward to `http://web:3000`. Caddy, for example:

    ```text title="Caddyfile"
    topos.example.com {
        reverse_proxy web:3000
    }
    ```

    `plane` needs no route at all. Give the proxy body-size headroom — a publish carries bundle
    bytes, and the ingest accepts roughly 160 MiB (`client_max_body_size 200m` in nginx; Caddy and
    Traefik do not cap by default). Make sure the proxy appends to `X-Forwarded-For` rather than
    replacing it — the rate belts key on the last hop.
  </Step>
  <Step title="Claim the workspace">
    Open `https://topos.example.com` in a browser once — the first browser request mints the
    workspace and prints the setup link:

    ```bash
    docker compose logs web | grep 'Finish setup:'
    ```

    Open that link and create the first account — that makes you **owner**. It is single-use and
    only the code's hash is stored; while the workspace is unclaimed every boot re-mints a fresh
    code after the next browser request, so a lost link is recovered by restarting the app. For
    CI/IaC, preset it with `TOPOS_SETUP_CODE=<at least 16 chars>` (or mirror the printed line to a
    file with `TOPOS_SETUP_LINK_FILE`).
  </Step>
  <Step title="Connect the first machine">
    ```bash
    topos login topos.example.com
    ```

    Name your server and the browser opens against it; a self-hosted install has one workspace,
    so the approval is a single click. Approve at `<origin>/verify`, and you are publishing.
  </Step>
</Steps>

### Verify it

```bash
curl -fsS https://topos.example.com/healthz
curl -fsS -H 'Accept: application/json' https://topos.example.com
```

Liveness answers `{"ok":true}`, and the protocol card answers
`{"schema_version":1,"card":"topos-protocol-card","api_base_url":"https://topos.example.com/api","server_version":"0.1.36","min_cli_version":"0.1.15"}`.
The last two fields are this deployment's compatibility declaration — the release it runs, and the
oldest `topos` it still speaks to (see [Upgrades](#upgrades)). In the checkout,
`bash scripts/compose-smoke.sh` runs the same end-to-end smoke the repo's CI does — it builds the
images from that tree and boots a throwaway stack, so it proves a source tree rather than your
running deployment.

<Warning>
  If `api_base_url` comes back as `http://…` or `localhost`, `TOPOS_PUBLIC_URL` is unset or wrong,
  and the CLI **refuses** to connect when an `https` address hands it a plain-http API base — that
  refusal is the symptom. `TOPOS_PUBLIC_URL` drives everything outward-facing: workspace addresses,
  the API base, invitation and verification links, and the printed setup link.
</Warning>

<Note>
  **Probing gotcha:** a non-browser fetch of any *page* gets the constant protocol card, not HTML —
  that is how clients discover the API base. Uptime checks and scrapers that expect a page must
  send `Accept: text/html`. The resource routes are the exceptions, answering any client with their
  own payload: `/healthz`, `/install`, `/compose.yml`, `/compose-init-db.sh`, `/llms.txt`, and the
  documentation's machine surfaces (`/docs.md`, `/docs/<page>.md`, `/docs/llms.txt`).
</Note>

## Mail

Topos has no built-in mail service. Configure an SMTP relay with all five variables — a partial set is
treated as unset:

```bash title=".env"
TOPOS_MAIL_SMTP_HOST=smtp.example.com
TOPOS_MAIL_SMTP_PORT=587        # port 465 means implicit TLS; others use STARTTLS
TOPOS_MAIL_SMTP_USER=topos@example.com
TOPOS_MAIL_SMTP_PASS=<secret>
TOPOS_MAIL_SMTP_FROM="Topos <topos@example.com>"
```

**Works without mail:** the claim ceremony, email + password sign-in, `topos login` approval,
publishing, review, delivery — the entire core loop.
**Needs mail:** inviting teammates (the mailbox round-trip is the identity proof), password-reset
mail, and magic-link sign-in (that option only appears on the sign-in page when mail can send).

Without SMTP an install is effectively single-user until you configure a relay or open registration:
**Settings → General → Registration → Open** (owner-only) lets anyone who can reach the origin
create an account — reasonable behind a VPN, think twice on a public origin.

<Tip>
  Forgot the only password on a mail-less install? Machine control is the proof:
  `node web/scripts/mint-recovery-code.mjs <email>` (run from a checkout against the same
  `DATABASE_URL`) prints a single-use 15-minute code to redeem at `<origin>/recovery`. The script
  is not in the runtime image — copy it in first with
  `docker compose cp web/scripts/mint-recovery-code.mjs web:/app/web/`.
</Tip>

## Workspace policy knobs

Policy lives in the product rather than in environment variables, so it is audited and changeable
without a redeploy. The review gate, the staleness window, session approval and expiry, and the
whole-catalog export are all on **Settings → General**, owner-only — see
[the table](/docs/team#policy). A self-hosted install has one knob more:

| Setting | Default | What it does |
|---|---|---|
| Registration | invite-only | Whether an uninvited sign-up succeeds |

## Upgrades

An upgrade is a tag and two commands. Check out the
[release](https://github.com/topos-sh/topos/releases) you want — the compose file, the provisioning
script and the two image pins move together — then pull it:

```bash
git fetch --tags && git checkout vX.Y.Z
docker compose pull && docker compose up -d
docker compose logs -f web
```

The last command confirms the boot migration ran. Both applications migrate their own schema at
boot, before binding a port — no migration command to run by hand, and a broken migration crashes
loudly rather than serving an unmigrated database.

**Back up first** — migrations apply automatically and there is no automated downgrade. Rolling
back is: stop the stack, restore the pre-upgrade backup, check out the previous tag, `pull` and
`up -d`, and pin clients to match (`topos self-update --version <tag>`).

Each side declares a compatibility floor, so an upgrade is not a fleet-wide chase. The server's
protocol card carries the release it runs and the oldest CLI it speaks to; every CLI carries the
oldest server it speaks to. Each floor sits at the last release that broke the wire in its own
direction — the CLI floor at `0.1.15`, the server floor at `0.1.36` today — and moves only when
the next break lands. A CLI below the server's floor is refused with one
sentence whose fix is `topos self-update`, and an agent reads the same refusal structurally and can
run it itself. A server below the CLI's floor is refused at `topos login`, before anything commits,
with both remedies named: ask whoever runs the server to upgrade it, or pin that machine back with
`topos self-update --version <tag>`. So after upgrading a server you do not hunt for machines —
anything too old refuses loudly, with the fix in the refusal. Pairings from before the mechanism
declare nothing and simply pass, until the next actual break.

<Warning>
  **Postgres major versions are not an in-place bump.** The bundled image is digest-pinned at
  PostgreSQL 18 and the volume is mounted at `/var/lib/postgresql` (18 moved its data directory).
  A pre-18 volume needs a `pg_dump` and restore into the new layout.
</Warning>

## Backups

All durable state lives in **two volumes** — and the order you snapshot them in matters:

| Volume | Holds |
|---|---|
| `plane-data` (`/data`) | The bytes: per-workspace git object stores and large objects |
| `pg-data` (`/var/lib/postgresql`) | Both schemas: identity, membership, catalog, channels, proposals, audit — plus the version index and `current` pointers |

<Warning>
  **Snapshot the bytes first, then the database.** A pointer in the database may name a byte
  written a moment ago. Bytes first, and the worst case is a few unreferenced blobs — harmless.
  Database first, and a pointer can name a byte your snapshot missed — a real hole.
</Warning>

```bash
docker run --rm -v topos_plane-data:/data -v "$PWD":/backup alpine \
  tar czf /backup/plane-data-$(date +%F).tar.gz -C /data .
docker compose exec -T db pg_dump -U topos -d topos --format=custom > topos-$(date +%F).dump
```

To restore: bring the stack down, restore the bytes volume, start only `db` and `pg_restore` into
it, then bring the rest up. **Restore the database before the app first serves a request** — on an
empty database the first-boot ceremony would mint a fresh workspace and claim link.

A backup deliberately covers none of: copies already delivered to people's machines (those are
theirs), client credentials (`~/.topos/identity/sessions.json` — losing it just means logging in
again), or your `.env` (rotating `TOPOS_WEB_AUTH_SECRET` signs every browser out).

## Bring your own Postgres

To use a managed database instead of the bundled `db`, run the provisioning script from your
checkout — the one the bundled database runs at first boot (idempotent, needs a superuser once).
Point `PGHOST`/`PGPORT` at your server:

```bash
POSTGRES_USER=<superuser> POSTGRES_DB=topos \
TOPOS_PLANE_DB_PASSWORD=<secret> TOPOS_WEB_DB_PASSWORD=<secret> \
  sh scripts/compose-init-db.sh
```

Take it from the release you are deploying rather than from `main`, so the roles it creates match
the images you pinned — in a checkout that is automatic; a deployment that skipped the clone
fetches it from `https://topos.sh/compose-init-db.sh`, which always serves the current recipe.

Then override each service's `DATABASE_URL` (append `?sslmode=require` for a networked database)
and start with `docker compose up -d --no-deps plane web`, keeping the bundled `db` down. Match
PostgreSQL 18, and verify the grant boundary the way the repo's CI does — it logs in as each role
and proves the grants hold:

```bash
sh scripts/check-db-grants.sh
```

A managed-database backup covers the metadata half only — **the `plane-data` volume is still yours
to back up.**

## Operating it

- **Health:** `GET /healthz` answers `{"ok":true}` — own-database liveness only, so a `plane`
  outage is never mistaken for a web outage. Point your platform's health check at it.
- **Logs:** the app logs to console — the setup line is the one deliberate stdout surface. `plane`
  logs JSON to stderr, filtered by `RUST_LOG` (default `info`).
- **Audit:** every mutation of shared state, including refused attempts, writes an attributed
  audit row — readable on each skill's and channel's History tab and under each settings knob.
- **Rate limiting:** the API belts key on the last `x-forwarded-for` hop. With **no** reverse
  proxy in front, every caller shares one bucket — set `TOPOS_WEB_RATELIMIT=off` and let your
  ingress do it.
- **Storage:** `plane` runs recovery, quarantine-janitor, and GC passes on an interval
  (`TOPOS_PLANE_GC_INTERVAL_SECS`, default 300). Watch the `plane-data` volume as version history
  grows.
- **Error reporting:** optional `SENTRY_DSN`, server-side only — no tracing, no cookies, no PII.

The rest of the environment surface (pool sizes, timeouts, bind addresses, migration paths) is
documented in the compose file and `topos-plane --help`.

## Known rough edges

- **No health checks for `web` or `plane` in the compose file** — only the database has one, so on
  a very first boot the app can render before `plane` finishes migrating. It settles on its own.
- **No metrics endpoint, no `/readyz`,** and no structured JSON logging on the web tier.
- **No zero-downtime upgrade procedure.** For a team-sized deployment, a brief restart is the
  expected shape.
