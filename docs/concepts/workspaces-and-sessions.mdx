## Workspace

A **workspace** is the org: one roster, one address, one catalog of skills, one audit trail. On the
cloud it is also the billable object.

Its address is how everyone reaches it:

| Deployment | Address shape |
|---|---|
| Topos Cloud | `https://topos.sh/acme` |
| Self-hosted | `https://topos.example.com` — the install *is* one workspace, rooted at its own origin |

Hand out the address and nothing else. **The roster is the lock** — links carry no authority, so
there is exactly one kind of link and "which link is this?" cannot be asked.

Every workspace is born with a default channel, `everyone`, which is implicitly part of every
member's profile.

## Seat

A **seat** is membership. One seat = **read access to the whole workspace catalog** — deliberately
git-clone-level trust, the same grade a team already extends to its git host.

Channels are **not** access control. They are curation. (Private channels are a considered, deferred
idea — they do not exist.)

Three roles, in three clean bands:

| Role | Can |
|---|---|
| **member** | Everything self-scoped; publish to open skills; create a channel; curate an open channel; invite is owner-only |
| **reviewer** | All of the above, plus approve/reject proposals, roll back, curate curated channels, see everyone's sessions |
| **owner** | All of the above, plus people, existence, and policy: invitations, roles, removal, protection loosening, archive/delete, workspace settings |

Everything is audit-trailed regardless of role.

<Note>
  **Agents do not manage people.** `invite` is the one roster verb in the CLI. Reading the roster,
  removing members, changing roles, and leaving a workspace are browser acts. Not everything on the
  web needs to be a command.
</Note>

## Session

A **session is one person × one workspace × one installation**, minted by `topos login`. The
credential it holds is scoped to that one workspace.

```bash
topos login https://topos.sh/acme     # mints a session
topos login https://topos.sh/beta     # a second workspace is a second login
topos logout acme                     # end one
topos logout --all                    # end them all on this installation
```

- One installation (one `~/.topos`, one OS profile) holds **many sessions — one per workspace**.
- Several OS profiles on one machine are independent installations, each with its own sessions.
- Sessions are revocable from **both sides**: by you, and by a workspace owner (stolen laptop,
  offboarding). An owner's revocation kills exactly that workspace's access and nothing else.
- Removing someone's seat ends their sessions in that workspace, in the same transaction.

### Local session states

| State | Meaning |
|---|---|
| `active` | Working normally |
| `pending` | Awaiting an owner's approval — **nothing is delivered** until it is approved |
| `ended` | The server answered its uniform 404: revoked, seat removed, or workspace gone — deliberately indistinguishable |

An ended session prints one typed line and then **freezes that workspace's items in place**. Nothing
is deleted. `topos login` reconnects.

### Where the credential lives

`~/.topos/identity/sessions.json`, mode `0600`. It is the one at-rest client secret, and losing it
just means logging in again. At-rest encryption is not implemented — full-disk encryption is the
right layer for that.

<Note>
  Applied-state reporting keys off sessions. **There is no machine-level content state.** A machine's
  only variation is which workspaces you logged it into.
</Note>

## Logging in

`topos login` is a browser-approval flow, `gh`-shaped:

```bash
topos login topos.sh/acme               # <server>/<workspace>
topos login acme                        # a bare name on the default server
topos login https://topos.example.com   # a bare origin — self-hosted
topos login https://topos.sh/acme/invite/<token>   # straight from the invite mail
topos login                             # resume a pending approval
```

The address is parsed by shape alone — no network call is needed to understand what you typed. Then:

<Steps>
  <Step title="Discover the API">
    Topos fetches the constant **protocol card** at the address's origin and reads the API base from
    it. An `https` address may never hand the flow to a plain-`http` base — the downgrade is refused.
  </Step>
  <Step title="Approve in a browser">
    A URL and a short code are printed. Where a browser is plausible, Topos opens the approval page
    for you on an ephemeral loopback listener so there is nothing to type. The short code itself
    never rides a URL, and the poll — not the redirect — remains the source of truth.
  </Step>
  <Step title="The session is minted">
    Approving mints the workspace-scoped credential. Re-running `topos login` resumes the same
    pending flow rather than starting a new one.
  </Step>
</Steps>

**Login is the acceptance event.** The receipt states what connecting delivers; from then on updates
arrive silently, npm-style. There is no per-bundle consent prompt for workspace content — in-org
bundles are higher-trust than a public registry, and protection against bad bundles is server-side
and *before* publish: review, curation, audit, visibility, and revert.

### Automation-safe behavior

| Situation | Behavior |
|---|---|
| A terminal, no `--json` | Blocks until the code expires |
| Piped output, no `--wait` | Prints the approval URL, polls once, exits `0`. **Never blocks** |
| `--wait` | Blocks; bare = until the code expires, `--wait 30` caps it at 30 seconds |
| `--json` | Never blocks and never opens a browser |

A browser is also suppressed when `SSH_CONNECTION`/`SSH_TTY` is set, or when `TOPOS_NO_BROWSER` is
set. In those cases you get the typed-code fallback.

<Warning>
  This is the single biggest hang risk when an agent drives Topos, and it is designed away: a piped
  `login` returns instead of polling for fifteen minutes.
</Warning>

### Session policy knobs

Owners control three settings that shape sessions, on the workspace settings page:

| Setting | Default | Effect |
|---|---|---|
| **Session approval** | off | On, a member's new login is born `pending` until an owner approves it. A session an owner mints is always born active |
| **Session expiry** | none | Past this age a session stops working and the machine logs in again. Skills already on it stay put |
| **Staleness window** | 7 days | How long without a report before a session reads *stale* on the sessions page |

Service accounts — CI, headless agents — are ordinary user-shaped principals with seats. Their
sessions live on runners.
