Your company tells everyone to use AI agents. Then every agent does the job its own way: one knows
the deploy checklist, one has a stale copy, one has never seen it. Processes drift, and nobody tells
an agent when a process changes.

**Topos fixes that.** A *skill* is a folder of files an agent reads and acts on — a `SKILL.md`,
maybe some scripts. Topos gives your team one shared home for those folders: publish a skill once,
and every teammate's agent has the current version at the start of its next session. Improve one
while working, and the improvement flows back to the team as a reviewable change.

## The fastest way in

Paste this to the agent you already use — Claude Code, Cursor, Codex, any of them:

```text title="Paste to your agent"
Set up Topos for us: fetch https://topos.sh/agent and follow it.
```

`topos.sh/agent` is a plain-text walkthrough written for agents; every Topos server serves its own
copy at `<origin>/agent`. Your agent will show you the install command before running anything, and
the one browser approval is always yours to click.

Prefer to type it yourself? Two commands:

```bash title="Terminal"
curl -fsSL https://topos.sh/install | sh
topos login https://topos.sh/<your-workspace>
```

## What using it looks like

<Steps>
  <Step title="Someone shares a skill">
    A teammate has a good `pr-describe` skill in their agent's skills folder.
    `topos publish pr-describe --yes` hands it to the workspace: one name, one version history, one
    movable `current` pointer that says what the team is on.
  </Step>
  <Step title="Everyone's agents get it">
    Machines logged into the workspace receive it automatically. A project can also pin the demand
    in a committed `topos.toml`, so everyone working in that repo gets the same set.
  </Step>
  <Step title="It stays current by itself">
    Logging in arms a session-start trigger that runs `topos update --quiet`. When the skill
    changes, the new bytes are on every machine at the next agent session — verified byte-for-byte,
    and never written over local edits.
  </Step>
  <Step title="Improvements come back">
    Someone sharpens the skill while working. `topos publish` offers it back — landing directly on
    an open skill, or opening a reviewable proposal on a protected one.
  </Step>
</Steps>

That is the whole loop: **distribute** and **contribute**. Everything else in these docs is detail
on one of those two motions.

## Two ways to run it

- **Topos Cloud** — hosted at [topos.sh](https://topos.sh). Sign up, create a workspace, hand out
  its address (`topos.sh/<name>`).
- **Self-hosted** — the entire product is Apache-2.0 in
  [one repository](https://github.com/topos-sh/topos) and runs from one compose file. Your
  workspace lives at your own origin.

Both run the same code. The CLI is identical; only the address differs.
