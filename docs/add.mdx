Most of the time you never run this. `topos login` connects the machine, and everything your team
has given you is already there — with every later change arriving on its own. `topos add` is for
the rest: pinning a set of skills to a repo so everyone working in it gets the same ones, or
pulling in a skill from outside your workspace.

## Connecting adopts what the team gave you

The moment a login is approved, this machine takes everything currently assigned to you and keeps
taking it. Four things put a skill in that set:

| Where it comes from | Who put it there |
|---|---|
| The **baseline** — the `everyone` channel | Every member has it, always |
| A **channel** you carry | A curator, or you |
| **Assigned to you** | Someone aimed that skill or channel at you — an invitation's first-destination hint does this too |
| **Picked by me** | You added it yourself from the library |

Your workspace's **Your skills** page shows exactly these four groups, each row saying which one it
is. Nothing to run, nothing to configure. On the machine:

```bash
topos list
topos list -g
```

Offline, and neither changes anything: what is installed where you stand, and — with `-g` — the
machine-wide set connecting gave you, each skill with its version and where it comes from.

## Turning one off

Two switches, with deliberately different reach.

<Tabs>
  <Tab title="Everywhere (the browser)">
    On **Your skills → Mine**, the toggle beside a skill turns it off for **you** — it stops
    arriving on every machine you log in. The row stays visible and dimmed, marked *off — still
    in the team library*, and turning it back on is one click. Nothing is deleted: copies already
    on a machine leave at that machine's next update.
  </Tab>
  <Tab title="This machine only (the terminal)">
    ```bash
    topos remove code-review -g
    topos add code-review -g
    ```

    Off here, then back on here. Both edit your own `~/.topos/topos.toml` — dropping the line that
    asked for the skill, or switching it `off` when the workspace still gives it to you — and say
    nothing about your other machines. The receipt points at the browser toggle when you meant
    everywhere.
  </Tab>
</Tabs>

<Note>
  Only you can decide this. The CLI never writes team-side state — turning a skill off for
  yourself is a browser act, and so is every act that reaches another person.
</Note>

## Add a set to a project

```bash
topos init
topos add code-review
topos add @acme/channels/backend
topos add ./tools/my-skill
topos add vercel-labs/skills/find-skills --yes
```

`topos init` writes the file, once, in the folder it should govern — the repo root, usually. Then,
in order: a skill from your workspace by name, a whole channel's set, a folder in this repo
(offline), and one skill from a public GitHub repo. The shape of what you type is the source — `@`
introduces a workspace, a slash without `@` is GitHub, a path is a folder. A pasted skill-page URL
works too, and `@acme/db-migrations@<version>` pins exact bytes.

Each `add` records **one line** in the nearest [`topos.toml`](/docs/topos-toml) at or above this
folder, and delivers in the same command:

```toml title="topos.toml — committed to the repo"
workspace = "topos.sh/acme"

[skills]
code-review = "latest"                       # the team's current version
my-skill    = "./tools/my-skill"             # a folder in this repo
find-skills = "github:vercel-labs/skills"    # a repo skill; moves on `topos update`

[channels]
backend = "latest"                           # a whole channel
```

**Commit that file**: everyone who works in the repo then gets the same skills, delivered to their
agents automatically. A line pointing at a folder in the repo vendors that skill outright — a
teammate clones, runs `topos update`, and has it, with no workspace involved. Every receipt reads
the same way — what was added and which file asks for it now, then where it came from:

```
added coolify-deploy to this project (./topos.toml) (undo: topos remove ./tools/coolify-deploy)
source: ~/work/acme-api/tools/coolify-deploy
```

The rest of the grammar — exact pins, placement, the `off` value, grouped keys, `topos fmt` — is
on [topos.toml](/docs/topos-toml).

With no `topos.toml` covering the folder you are standing in, `add` stops and says so, pointing at
`topos init` here or `-g` for your machine. It never creates a file behind your back, and never
quietly writes to the other one.

## Add something just for this machine

```bash
topos add code-review -g
```

`-g` edits `~/.topos/topos.toml` — this machine's own list — instead of the project's. That file
is the **complete** list for this machine: what it names is what you get. Most of it writes
itself — `topos login` records a workspace's feed line (`[workspaces] "topos.sh/acme" = "latest"`) the first time
this machine connects, so everything the workspace gives you flows with no editing. Delete a feed
line and it stays deleted (login never re-adds it); a `-g` add then records exactly the lines you
choose.

<Tip>
  A `-g` add of something the team already gives you writes nothing and says so. There is no
  point stacking a line on top of a line that already delivers — unless you pin it, which is a
  real conversion to machine-local control.
</Tip>

## Two lists that never blend

The nearest `topos.toml` above your working directory governs that checkout **whole**, and your own
file governs this machine — no merging, and no arithmetic between them. They answer two different
questions: "what should anyone working here have?" and "what should follow me around?" So a skill
named by both is delivered twice, once into the project's agent directories and once into your home
ones; they update independently, and `topos list <skill>` names which file and line — or which
workspace's set — is behind each copy. Their bookkeeping is separate too: a skill added inside a
checkout keeps its version history in that checkout's own `.topos/`, so your machine's store and
home agent directories never mention it. More: [topos.toml](/docs/topos-toml).

No command crosses that line on its own. Every verb acts on where you stand — the nearest
`topos.toml` when one covers the folder, your machine otherwise — and `-g` on any verb means the
machine. What a verb doesn't act on is never hidden either: it comes back as one summary line
ending in the exact command that expands it.

## Where the files land

Skills go into the folders the agents you picked actually read: `~/.claude/skills/<name>` for
your machine-wide set, `.claude/skills/<name>` and its siblings inside a checkout. One folder per
agent, and nothing for an agent you did not pick. The full table:
[Supported agents](/docs/harnesses).

Some of those folders are links rather than files — one bundle installs itself once and links each
skill into every agent's directory. Adding one of those adds the **original**: the folder the bytes
actually live in, which is what the line records and what the `source:` line names. Nothing in
either folder changes.

## A copy you already have

```bash
topos add ~/.codex/skills/coolify-deploy --as coolify-deploy -g
```

Sometimes the skill is already sitting in an agent's folder — you copied it there yourself, or it
arrived before topos did. `--as` brings that folder under management **as the skill you already
have**, instead of recreating it beside itself:

```
added ~/.codex/skills/coolify-deploy as a copy of coolify-deploy — nothing in it changed; updates land here from now on
source: topos.sh/ideamotive/coolify-deploy
```

Nothing in the folder is touched at claim time. What happens next depends only on what the bytes
are: identical to the current version, it is simply one more place the skill is; an older version,
and the next update brings it current; anything else becomes **your draft** of that skill — saved
first, then spread to its other folders and offered by `topos publish`. The receipt says which.

`--as` takes a folder and the name (or full reference) of a skill this scope already manages —
never a workspace catalog, and never the other scope. A folder some other skill already holds
refuses by name rather than letting two records fight over one directory. If topos had already
placed its own copy next to yours under a suffixed name, that duplicate goes with the claim,
unless you had edited it. Running the same claim twice changes nothing, and says so.

The inverse is `remove <skill> --dest <folder>` — which answers to the folder itself or to the
folder holding it, spelled either way:

```
removed ~/.codex/skills/coolify-deploy from coolify-deploy — the folder and its files stay; it just stops updating
```

Adding a skill you already have says so — and, when unmanaged folders on this machine provably
hold a version of it, lists them as exactly these commands.

## Pick which agents get it

```bash
topos add @acme/deploy-checklist -a codex -g
topos add @acme/deploy-checklist --dest ~/team-skills -g
topos remove deploy-checklist -a codex -g
```

By default a skill reaches every agent you picked here. `-a <agent>` (repeatable) narrows it to
exactly those agents, and each one has to be in your pick already: name an agent outside it and the
add refuses, pointing at `topos agents add <agent>`. The flag is sugar for that agent's own skills
folder. `--dest <folder>` names an exact folder, which the pick does not govern; together the union
is the destination set. The choice is recorded on the line itself (`dest = ["~/.codex/skills"]`), so
every later update keeps the copy where you asked. For an MCP server, `-a` picks whose config file
gets the entry.

The same flags on a later `add` **set** the destinations again: the line ends up with exactly what
that run named, which is how you re-aim a line as well as how you first aim it. Naming what the
line already has changes nothing, and says so.

When a channel or workspace line already delivers the bundle and it has no line of its own, there
is nothing to record: a line written here could only narrow what that channel reaches. The add
places the copy the agent you named was missing and says which line delivers it:

```
sentry already reaches every agent here through channels/everyone — no row to record.
Placed the copy that was missing:
  opencode: opencode.json — created
```

A folder no agent owns is the one exception: nothing but a line reaches it, so `--dest <that
folder>` does write one — carrying `"*"`, so everything the channel reaches rides along — and the
receipt closes by saying how to hand the bundle back to the channel alone.

The same flags on `remove` **subtract**: only that agent's copy leaves, the line keeps the rest,
and the receipt says what remains (`removed (~/.codex/skills) — 2 folders remain`). Removing the
last destination removes the line. On a line that named no destinations, a subtraction first
writes out the line's current set minus the removed one — the receipt disclosing exactly that.
Inside a repo, delivered folders keep **themselves** out of commits: each carries a one-line
`.gitignore`, the way `node_modules` does. Topos writes nothing under `.git/` and never touches an
ignore file you wrote. Its bookkeeping for that checkout lives in `<project>/.topos/`, which also
ignores itself.

## Updates apply themselves

Logging in registers a session-start trigger, so each time an agent starts the machine quietly catches
up — that sweep always covers both sets, this folder's and your machine's, so nothing goes stale
while you work in one place. By hand, any time:

```bash
topos update
topos update -g
topos update code-review
topos update code-review@<version>
topos update --force
```

Everything the scope you are standing in asks for — this folder's `topos.toml` when one covers it,
your machine-wide set otherwise; then the machine-wide set explicitly; one skill inside that scope;
that version's bytes put back on this machine only; or every managed folder re-created from topos's
own store, for the rare folder that is still there but damaged. Each receipt names the scope it
acted on.

New files are verified against the workspace's records before anything lands, and **your local
edits are never overwritten** — updates merge around them, and a genuine conflict stops the merge,
with both ways out named on the receipt. Details:
[Review, protect, roll back](/docs/review#your-edits-are-safe).

One thing deliberately does **not** move on its own: a pinned version. Everything else is kept
current for you, GitHub lines included — those are checked a few times a day rather than at every
session start, because a forge answers about one repository per request and a whole office can
share one allowance. The check itself is cheap: Topos asks what commit the repo is on now and
downloads it only when that has actually changed. When something moves, the receipt names the
commit it moved to and which skills appeared or disappeared. `topos update`, typed by hand, checks
everything immediately.

## Import from GitHub

```bash
topos add vercel-labs/skills
topos add vercel-labs/skills/find-skills
topos add vercel-labs/skills@e173b8c
```

Every skill the repo holds, one of them, or the repo frozen at a commit. A bare run shows what it
found — the source, the skills in it, and the exact line it would write — and changes nothing. Read
it, then apply with `--yes`. That happens every time you add from a repo, not just the first: the
listing is the point of typing the command.

<Warning>
  A skill is instructions your agent will follow, and Topos verifies nothing about a third-party
  repo's contents. That listing is there to be read.
</Warning>

Without a pin, a repo entry tracks its default branch. To freeze one, give a commit — or paste a
GitHub URL that already names a tag or branch (`.../tree/v1.2.0/skills/find-skills`) and the entry
records the commit that tag resolved to, so the freeze can't drift under you.

Publish an imported skill to your workspace and the workspace starts watching the source repo —
new upstream commits arrive as review proposals, never as silent changes. There is also a browser
import with a preview at `<origin>/skills/import`.

## Add an MCP server

```bash
topos add weather                             # one your workspace already shares
topos add --kind mcp io.github.acme/weather   # share a new one, and get it here
topos add --kind mcp https://acme.example/server.json
```

An MCP server is a **bundle like any other**: it records the same one line, but your agents get it
as a tool endpoint in their own MCP config instead of as a skill folder. One your workspace already
shares needs no flag — the workspace records what each bundle is.

`--kind mcp` is how a NEW one gets shared. The name (or the link) goes to your workspace: the
server reads the document, rules on whether it may be shared, and answers with the name it shares
it as — then the row lands here and your agents' configs converge, in the same command. A name your
install's catalog already carries is a connection any member may make; anything else writes your
workspace's own server down, which an owner does.

A folder on your machine holding a `server.json` is not shared at all — it is a line you write in
your own `topos.toml` (`"~/work/weather" = { kind = "mcp" }`), read fresh on every update. A
plain `topos add ./that-folder` refuses rather than landing it as a skill, and says both ways out.

An add applies immediately, and the receipt leads with the undo: what the server is, its endpoint,
whether a sign-in is coming, which agents it reached, and the one `topos remove` that takes it
back. What Topos refuses to place, and why: [MCP servers](/docs/mcp).

## Stop receiving

```bash
topos remove code-review
topos remove code-review -g
```

From this project, or from your own machine-wide list. `remove` edits the same file `add` did and
prints the undo — they are exact inverses, and neither reaches across: a skill your machine-wide
file delivers is refused here, pointing at `-g`. Removing a line also uninstalls the copies it
placed, in the same command; an edited copy is never swept up with the removal — it stays on disk
where you made it, and the receipt says so (`kept <name> — <path> is edited`). One case describes
first instead of applying:

- **The line covers a set.** Removing one skill out of a channel or a whole-repo entry means
  replacing that one line with its current members — after which later additions by whoever curates
  it stop arriving through this file.

Bigger exits: `topos logout` stops one workspace's delivery to this machine (skills and your edits
stay); `topos uninstall --yes` removes topos entirely — without deleting a single skill file. And
if the workspace removes a skill or your access, delivery just stops: your local copies and edits
are always retained.

## Check any time

```bash
topos list
topos list db-migrations
topos list --untracked
topos list --remote
topos status
```

The inventory where you stand, each skill with its version and source; one skill in depth — the
exact file and line behind it, or the workspace feed, and where its files sit; the skills already in
your agents' folders that topos doesn't manage yet; what your workspaces offer, the one command here
that needs the network; and the health panel — logins, sessions, whether the auto-update triggers
are registered, and what needs attention, each with the command that resolves it.

Nothing a view leaves out is hidden: a bare `topos list` inside a project ends with one line for the
machine-wide set and one for the untracked skills, each naming the command that opens it in full.
