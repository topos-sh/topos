Most of the time you never run this. `topos login` connects the machine, and everything your team
has given you is already there — with every later change arriving on its own. `topos add` is for
the rest: pinning a set of skills to a repo so everyone working in it gets the same ones, or
pulling in a skill from outside your workspace.

## Connecting adopts what the team gave you

The moment a login is approved, this machine takes everything currently assigned to you and keeps
taking it. Four things put a skill in that set:

| Where it comes from | Who put it there |
|---|---|
| The **baseline** — the `everyone` channel | Every member has it, always |
| A **channel** you carry | A curator, or you |
| **Assigned to you** | Someone aimed that skill or channel at you — an invitation's first-destination hint does this too |
| **Picked by me** | You added it yourself from the library |

Your workspace's **Your skills** page shows exactly these four groups, each row saying which one it
is. Nothing to run, nothing to configure. On the machine:

```bash
topos status
```

Offline, and it changes nothing: every skill here, its version, and what asked for it.

## Turning one off

Two switches, with deliberately different reach.

<Tabs>
  <Tab title="Everywhere (the browser)">
    On **Your skills → Mine**, the toggle beside a skill turns it off for **you** — it stops
    arriving on every machine you log in. The row stays visible and dimmed, marked *off — still
    in the team library*, and turning it back on is one click. Nothing is deleted: copies already
    on a machine leave at that machine's next update.
  </Tab>
  <Tab title="This machine only (the terminal)">
    ```bash
    topos remove code-review -g
    topos add code-review -g
    ```

    Off here, then back on here. Both edit your own `~/.topos/topos.toml` — dropping the line that
    asked for the skill, or switching it `off` when the workspace still gives it to you — and say
    nothing about your other machines. The receipt points at the browser toggle when you meant
    everywhere.
  </Tab>
</Tabs>

<Note>
  Only you can decide this. The CLI never writes team-side state — turning a skill off for
  yourself is a browser act, and so is every act that reaches another person.
</Note>

## Add a set to a project

```bash
topos add code-review
topos add @acme/channels/backend
topos add ./tools/my-skill
topos add vercel-labs/skills/find-skills --yes
```

In order: a skill from your workspace by name, a whole channel's set, a folder in this repo
(offline), and one skill from a public GitHub repo. The shape of what you type is the source — `@`
introduces a workspace, a slash without `@` is GitHub, a path is a folder. A pasted skill-page URL
works too, and `@acme/db-migrations@<version>` pins exact bytes.

Each of those records **one line** in the nearest [`topos.toml`](/docs/topos-toml) — this folder's,
or a fresh one at the repo root when there isn't one yet — and delivers in the same command:

```toml title="topos.toml — committed to the repo"
[bundles]
"topos.sh/acme/code-review" = "*"                       # the team's current version
"topos.sh/acme/channels/backend" = "*"                  # a whole channel
"./tools/my-skill" = "*"                                # a folder in this repo
"github.com/vercel-labs/skills/find-skills" = "*"       # tracks the repo; moves on `topos update`
```

**Commit that file**: everyone who works in the repo then gets the same skills, delivered to their
agents automatically. Every receipt names the file it edited and the exact undo. The rest of the
grammar — exact pins, placement, the `off` value, grouped keys, `topos fmt` — is on
[topos.toml](/docs/topos-toml).

## Add something just for this machine

```bash
topos add code-review -g
```

`-g` edits `~/.topos/topos.toml` — this machine's own list — instead of the project's. Most people
never have that file and don't need one: while it is absent, the machine behaves exactly as if it
said "everything each connected workspace gives me". The first `-g` command writes it out in full
before making your edit, one line per workspace you're connected to, so you can see what you
already had. From then on that file is the **complete** list for this machine: what it names is
what you get.

<Tip>
  A `-g` add of something the team already gives you writes nothing and says so. There is no
  point stacking a line on top of a line that already delivers — unless you pin it, which is a
  real conversion to machine-local control.
</Tip>

## Two lists that never blend

The nearest `topos.toml` above your working directory governs that checkout **whole**, and your own
file governs this machine — no merging, and no arithmetic between them. They answer two different
questions: "what should anyone working here have?" and "what should follow me around?" So a skill
named by both is delivered twice, once into the project's agent directories and once into your home
ones; they update independently, and `topos status <skill>` names which file and line — or which
workspace's set — is behind each copy. More: [topos.toml](/docs/topos-toml).

## Where the files land

Skills go into the folders your agents actually read — `~/.claude/skills/<name>`, the shared
`~/.agents/skills/<name>`, or a project's own agent directories. The full table:
[Supported agents](/docs/harnesses).

Inside a repo, delivered folders keep **themselves** out of commits: each carries a one-line
`.gitignore`, the way `node_modules` does. Topos writes nothing under `.git/` and never touches an
ignore file you wrote. Its bookkeeping for that checkout lives in `<project>/.topos/`, which also
ignores itself.

## Updates apply themselves

Logging in arms a session-start trigger, so each time an agent starts the machine quietly catches
up. By hand, any time:

```bash
topos update
topos update code-review
topos update code-review@<version>
topos update --rebuild
```

Everything; one skill; that version's bytes put back on this machine only; or every managed folder
re-created from topos's own store.

New files are verified against the workspace's records before anything lands, and **your local
edits are never overwritten** — updates merge around them, and a genuine conflict is frozen with a
named way out. Details: [Review, protect, roll back](/docs/review#your-edits-are-safe).

Two things deliberately do **not** move on their own: a pinned version never moves, and a git
source moves only when you run `topos update` yourself. The quiet session-start sweep never
contacts GitHub, so no agent session pays for a round-trip to a forge; when you do run it, the
receipt names the commit it moved to and which skills appeared or disappeared.

## Import from GitHub

```bash
topos add vercel-labs/skills
topos add vercel-labs/skills/find-skills
topos add vercel-labs/skills@e173b8c
```

Every skill the repo holds, one of them, or the repo frozen at a commit. The first time you add
from a repo, a bare run shows what it found — the source, the skills in it, and the exact line it
would write — and changes nothing. Read it, then apply with `--yes`. After that the source is
trusted here and further adds from it land immediately with an undo-led receipt.

<Warning>
  A skill is instructions your agent will follow, and Topos verifies nothing about a third-party
  repo's contents. That first listing is there to be read.
</Warning>

Without a pin, a repo entry tracks its default branch. To freeze one, give a commit — or paste a
GitHub URL that already names a tag or branch (`.../tree/v1.2.0/skills/find-skills`) and the entry
records the commit that tag resolved to, so the freeze can't drift under you.

Publish an imported skill to your workspace and the workspace starts watching the source repo —
new upstream commits arrive as review proposals, never as silent changes. There is also a browser
import with a preview at `<origin>/skills/import`.

## Stop receiving

```bash
topos remove code-review
topos remove code-review -g
```

From this project, or from your own machine-wide list. `remove` edits the same file `add` did and
prints the undo — they are exact inverses. Two cases describe first instead of applying:

- **Local work would be lost.** A skill you've edited but not shared is described first, so you can
  see the draft before the copy leaves your agent directories. (Your edits are snapshotted, never
  deleted.)
- **The line covers a set.** Removing one skill out of a channel or a whole-repo entry means
  replacing that one line with its current members — after which later additions by whoever curates
  it stop arriving through this file.

Bigger exits: `topos logout` stops one workspace's delivery to this machine (skills and your edits
stay); `topos uninstall --yes` removes topos entirely — without deleting a single skill file. And
if the workspace removes a skill or your access, delivery just stops: your local copies and edits
are always retained.

## Check any time

```bash
topos status
topos status db-migrations
topos list
topos list --remote
```

Every skill here with its version and source; one skill in depth — the exact line behind it and
where its files are; the inventory plus untracked skills you could add; and what your workspaces
offer.
