Logging in already delivers your team's shared baseline — anything in the `everyone` channel
arrives on its own. `topos add` is for the rest: pinning a set to a project, following a
narrower channel, or pulling in a skill from outside.

## One command, three kinds of source

```bash
topos add code-review             # from your workspace, by name
topos add @acme/channels/backend  # a whole channel's set
topos add ./tools/my-skill        # a local folder, offline
topos add vercel-labs/skills      # a public GitHub repo
```

The shape of what you type is the source: `@` introduces a workspace, a slash without `@` is
GitHub, a path is a folder. A pasted skill-page URL works too, and `@acme/deploy@<version>`
pins exact bytes. Every receipt names the file it edited and the exact undo command.

## For this project, or for you

<Tabs>
  <Tab title="This project (default)">
    ```bash
    topos add code-review
    ```

    Records the skill in the repo's `topos.toml`. **Commit that file** — everyone who works
    in the repo then gets the same skills, delivered to their agents automatically.
  </Tab>
  <Tab title="For you (-g)">
    ```bash
    topos add code-review -g
    ```

    Adds it to your profile instead: it follows you to every machine you log in on. You can
    edit the same list in the browser, under **Your skills**.
  </Tab>
</Tabs>

`topos.toml` is plain TOML, and editing it by hand is fully supported:

```toml title="topos.toml"
exclude = ["topos.sh/acme/noisy-skill"]  # don't deliver this one here

[skills]
"topos.sh/acme/code-review" = "*"            # the team's current version
"topos.sh/acme/deploy" = "<64-hex version>"  # pinned to one version
"github.com/vercel-labs/skills/skills/find-skills" = "e173b8c"  # pinned
"./tools/my-skill" = "*"                     # a folder in this repo

[channels]
"topos.sh/acme/channels/backend" = "*"
```

When several files ask for the same skill, the nearest wins: this folder's `topos.toml`,
then parent folders', then your profile. `topos status` names the exact line behind every
skill on the machine.

## Where the files land

Skills are placed into the folders your agents actually read — `~/.claude/skills/<name>`,
the shared `~/.agents/skills/<name>`, or the project's own agent directories. Inside a repo,
one line in `.git/info/exclude` keeps placements out of commits; committed ignore files are
never touched. The full directory table: [Supported agents](/docs/harnesses).

## Updates apply themselves

Logging in arms a session-start trigger: each time an agent starts, the machine silently
catches up. By hand, any time:

```bash
topos update                        # everything
topos update code-review            # one skill
topos update code-review@<version>  # roll back this machine only
```

New files are verified against the workspace's records before anything lands, and **your
local edits are never overwritten** — updates merge around them, and a genuine conflict is
frozen with a named way out. Details:
[Review, protect, roll back](/docs/review#your-edits-are-safe).

## Import from GitHub

```bash
topos add vercel-labs/skills                 # a public repo
topos add vercel-labs/skills -s find-skills  # one skill from a repo
topos add owner/repo#v1.2.0                  # a tag, branch, or commit
```

GitHub entries behave like lockfile lines: pinned to a commit, moving only when you bump the
pin. Publish an imported skill to your workspace and the workspace starts watching the source
repo — new upstream commits arrive as review proposals, never as silent changes. There is
also a browser import with a preview at `<origin>/skills/import`.

<Warning>
  A skill is instructions your agent will follow, and Topos verifies nothing about a
  third-party repo's contents. Read what you import.
</Warning>

## Stop receiving

```bash
topos remove code-review     # from this project
topos remove code-review -g  # from your profile, every machine
```

`remove` edits the same file `add` did and prints the undo. When something broader — a
channel, the team baseline — still provides the skill, the receipt says an opt-out line was
recorded here instead. It asks first only when local work would be lost.

Bigger exits: `topos logout` stops one workspace's delivery to this machine (skills and your
edits stay); `topos uninstall --yes` removes topos entirely — without deleting a single
skill file. And if the workspace removes a skill or your access, delivery just stops: your
local copies and edits are always retained.

## Check any time

```bash
topos status         # every skill here, its version, and its source
topos list           # inventory, plus untracked skills you could add
topos list --remote  # what your workspaces offer
```

`topos status` works offline and changes nothing — it names the exact line that asked for
every skill on the machine.
